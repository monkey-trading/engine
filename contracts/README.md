# Custody vault

`Vault.sol` holds six-decimal USDC collateral on Arbitrum One. The deterministic engine owns trading balances and the FIFO withdrawal queue. The vault accepts deposits, stores enclave-signed checkpoints, and pays signed approvals proven against an accepted checkpoint. If checkpoints stop, anyone can start its exit against the last posted root. It is not upgradeable.

Deposits accept 10 to 1e9 USDC per call. `deposit`, `depositFor` and `depositToHouse` share one deposit-id sequence. The events report the tokens actually received, including for a token with an incoming transfer fee. The engine credits finalized events once by transaction hash and log index.

`totalDeposited()` counts the USDC base units every deposit brought in, and `depositedThrough(id)` holds that total just after deposit `id`, so the node compares its ledger with exactly the deposits it has credited while later ones are still in flight. USDC that reaches the vault outside a deposit, such as a direct transfer, is a surplus: the token balance plus `totalWithdrawn()` and `distributionsPaid()` exceeds `totalDeposited()`. A surplus does not pause withdrawals; the node raises a Warning until it is booked. Anyone may call `bookSurplus()` to record it as a house deposit, a `HouseDeposited` event from the caller in the same id sequence, at most 1e9 USDC per call. A surplus below the 10 USDC minimum reverts with `NoSurplus` and must be topped up first.

## Governance and deployment

Deploy an [OpenZeppelin `TimelockController`](https://docs.openzeppelin.com/contracts/5.x/api/governance#TimelockController) with a deployment-selected, nonzero minimum delay and the deployment's multisig as proposer. Configure executor and administrator roles deliberately; the timelock must administer itself after setup. Pass that deployed timelock as the third Vault constructor argument, after the token and attestation-verified enclave signer, the multisig's own address as the fourth, the guardian, and the engine's initial MONKEY emission period budget as the fifth, which caps the MONKEY token the vault deploys and alone mints. The sixth to eighth are the exit period, the claim window and the deposit staleness, in seconds (see Exit below). The Vault constructor checks that the timelock has code and a nonzero delay, that the exit period exceeds that delay, and that the claim window and staleness are nonzero with the staleness at most the exit period. Deployment must verify the supplied contract is the intended OZ implementation and that its roles belong to the intended multisig; a Solidity address/type cannot establish those facts.

Only calls executed by the timelock may invoke `setSigner(address)`, `setCurrentRelease(bytes launchDigest, bytes32 configHash)`, or `setPauses(bool depositsPaused, bool withdrawalsPaused)`; the guardian is not the timelock and cannot call them. `setCurrentRelease` records `currentRelease = keccak256(launchDigest ‖ configHash)`: the one enclave release, a 48-byte SEV-SNP launch measurement running the config file with that SHA-256, that may hold the enclave's keys. Nodes read it at custody finality: a node opens or seals keys only while it names the node's own release, and the running release hands its keys only to the release it names, so setting a new one supersedes the old. While the vault's named registry has rotation on (its `rotationEnabled()`), `currentRelease` is instead the registry's named operator's release, which moves to a promoted standby at once, and `setCurrentRelease` reverts `RotationActive`; `syncRelease`, callable by anyone, folds a registry-driven release change into a new `releaseGeneration` so a standby seals keys only after the change is counted, and `syncedRelease()` is the release last folded. While a daily turn names the operator, the turn holds the generation instead (see Daily operator turns below). Every call raises `releaseGeneration`, even for a release named before or the current one: a node seals its keys under the generation it runs in and opens only a copy sealed under the current one, so a release named again takes the keys afresh from the running release instead of reopening an older copy. It changes no signer or epoch, so outstanding authorizations stay valid across an upgrade or config change, and `CurrentReleaseChanged` records each change with its generation, measurement and config hash. A launch digest of any other length reverts with `InvalidLaunchDigest`. Signer changes increment `signerEpoch`, initially 1, including when the same address is reused. Besides the timelock's `setSigner`, only the registry's schedule may change the signer, with `promoteSigner(address)` (`UnauthorizedSchedule` for any other caller): it installs a promoted member's vouched standby key in a new epoch with no timelock delay and no registered-enclave check, and reverts once the exit has started (`ExitActive`), while the guardian has retired the signer (`NoSigner`), and for the zero address. Every signer change, by either path, records `signerSince()`, the block time the schedule's miss count restarts from, and `wasSigner(address)` marks every address ever installed, which the schedule never promotes. Both checkpoint and withdrawal verification use the current `checkpointSigner`. Rotation immediately invalidates old withdrawal epochs; current-key reissues retain the original account, amount, nonce and approval sequence. The nonce-use mapping survives rotation. `signerAtEpoch(epoch)` preserves each assigned epoch's signer for replay authentication, including epochs with no checkpoint, while claims and checkpoints still require the current signer. `SignerChanged` and `PausesChanged` record administration.

Deposit pause covers every deposit route, including house capital and `bookSurplus`. Withdrawal pause blocks withdrawal and distribution claims without consuming nonces. The flags are independent; checkpoint posting remains available during either pause. Changing either flag requires the configured timelock delay.

The guardian, an immutable address set at deployment to the multisig, acts at once, without the delay, in an emergency such as a possibly compromised enclave signer. It can do two things and nothing else. `pauseWithdrawals()` pauses withdrawal and distribution claims for `GUARDIAN_PAUSE`, seven days, emits `GuardianPausedWithdrawals(until, pauses)` and increments the public `guardianPauses()` counter; it reverts while withdrawals are already paused, so the guardian cannot extend a pause in force. The timelock renews a pause by pausing withdrawals itself, which holds until it unpauses, and its `setPauses` with withdrawals unpaused also ends a guardian pause early. `withdrawalsPausedUntil()` is the end of the current pause, `type(uint256).max` for the timelock's. `retireSigner()` clears `checkpointSigner` and emits `SignerRetired(signer, signerEpoch)`: no withdrawal signed in the current epoch, no checkpoint, and no MONKEY or USDC claim on a root of that epoch is accepted again, and the retirement never expires; `setSigner` through the timelock then starts the next epoch, whose first checkpoint claims prove against. Retiring leaves `signerEpoch` and `signerAtEpoch` unchanged and reverts with `NoSigner` once retired. A guardian pause alone does not stop emission claims. Deposits and `bookSurplus` are unaffected by either. Timelock delay/role changes themselves follow OZ governance; the deployment must preserve its intended delay and proposer policy.

This change requires a new Vault deployment and constructor updates in deployment clients. It provides no migration of an existing Vault's balances, accepted roots or used nonces. The signing node must read the current signer epoch and reconcile against the deployed Vault before releasing authorizations.

## Staking and the operator election

`Staking.sol` holds staked MONKEY, enforces the unstake cooldown, and emits `Staked`, `UnstakeStarted` and `UnstakeCompleted`. New stake is undelegated, and undelegated stake abstains. A staker delegates chosen amounts of its undelegated stake to any number of candidates with `delegate(candidate, amount)`, moves an amount from one candidate to another in one call with `redelegate(from, to, amount)`, and takes an amount back with `undelegate(candidate, amount)`, which emit `Delegated`, `Redelegated` and `Undelegated` with the amount. `delegatedTo(staker, candidate)` is one delegation, `delegatedStake(staker)` the part of the stake its delegations hold, and `delegationsOf(staker)` every delegation in one call. `votes(candidate)` is the sum of the amounts delegated to it, and `totalStaked()` excludes unstaking amounts. `startUnstake` takes undelegated stake first, then reduces each delegation in proportion: from the last in `delegationsOf` order to the first, each gives the amount still to take times its share of the delegations not yet reduced, rounded down, so the first gives exactly what remains and the votes stay exact. It emits `Undelegated` for each reduction before `UnstakeStarted`, so the events alone track every delegation. Votes drop at `startUnstake`, though the unstaking amount keeps earning distributions through the cooldown. A staker may hold any number of delegations. An unstake no larger than the undelegated stake reads none of them; a larger one costs about 16k gas for each delegation it reduces and 25k for each it empties (`test_GasOfAnUnstakePerDelegation` reports both), so a staker with many delegations takes some back first, each call touching one or two, to keep the unstake within the block gas limit. Delegation changes nothing about distributions.

`OperatorRegistry.sol` names the operator whose key signs the engine's admin commands: by election, or, once the timelock names an operator schedule, by daily turns (see Daily operator turns below). Its constructor deploys `Staking`, which records the registry as the only caller of `lockBond` and `releaseBond`; deploy `Staking` only this way. The constructor takes the MONKEY token, the staking cooldown and distribution epoch, the timelock, the initial operator in effect (its admin key, 48-byte launch measurement, and config hash), and the election parameters with the lowest and highest value of each. The parameters are the epoch length, the finality margin, the eligibility share and quorum in basis points of total stake, the candidate cap (at most `CANDIDATE_LIMIT`, 100, which bounds a close's gas), and the minimum self-bond. Their production values and bounds are not set here.

- `register` records the caller's admin key, self-bond, API hostname, handover endpoint and release, `keccak256(launchDigest ‖ configHash)` as the vault names a release, and locks the self-bond in `Staking`; it carries the admin key's EIP-712 authorization of the candidate (`registrationDigest`, the same typed-data vocabulary as the vault's withdrawals), so a key is registered only for a candidate it authorized. `startUnstake` cannot take it while the candidate is registered nor for one cooldown after `deregister`. Admin keys are unique among candidates. The operator in effect while no turn names one, a candidate elected and waiting to take effect, and a member holding a turn cannot deregister.
- The timelock's `setReleaseApproval` approves a candidate's own release. Approval lists the candidate in `candidateList` under the candidate cap — only approved candidates count toward the cap and enter the list, so unapproved registrations cannot fill it; withdrawing approval delists the candidate while it stays registered, and a re-registration whose release is still approved relists at once.
- A candidate moves its candidacy to another release the timelock approved for it with `setRelease`, reverting `ReleaseNotApproved` otherwise. A move is one-way: it withdraws the approval of each release it leaves — the candidacy's, and for the operator in effect the one it ran, which the deployment or an installation may have named apart from its candidacy — reporting each approval withdrawn (`ReleaseApprovalChanged(candidate, left, false)`), so moving back needs a new approval. A delisted candidate's move relists it under the cap, so keeping a candidate off the list means withdrawing every release approved for it; the operator in effect may take one place beyond the cap, so a full list never blocks its upgrade, unless an operator an installation replaced took that place first: the list stays at most one over the cap, and the timelock frees a place by withdrawing an approval or raising the cap. When the caller is the operator in effect, its operator release moves too, so while rotation is on the vault names the new release at once and `syncRelease` raises the generation: this is how the operator in effect upgrades while `setCurrentRelease` is closed to the timelock. An installed operator moves the same way once it is registered, with the approvals the timelock granted its candidacy; an installation changes no candidacy, so the operator it replaces keeps its release, approvals and listing, and its moves no longer reach the vault. While an election or promotion waits to take effect, the operator it replaces and the candidate it names cannot move (`ElectionPending`), so the pending release and the handover source stay as the election made them. `CandidateReleaseChanged` reports each move.
- A candidate is eligible while it is listed, its self-bond meets the minimum, and its votes meet the eligibility share.
- Anyone calls `closeEpoch` once the open epoch has ended; unclosed epochs are skipped. With a schedule named, a close while rotation is on adopts a rotation set and never elects. Without one, while rotation is on and no election waits to take effect, the close elects the eligible candidate with the most votes, the earlier registration on a tie, when it is not the operator in effect and listed candidates' votes reach the quorum: the operator in effect serves no minimum term, and keeps the role on a tie only when it registered first. `Elected` names the epoch, candidate, admin key, release, and the effective time, seven days plus the finality margin after the close. `operatorInEffect()` returns the election from that time.
- Only the timelock calls `setRotation`, off at deployment with the initial operator in effect; turning it off cancels an election not yet in effect, which `RotationChanged(false, true)` reports. It also approves releases and calls `setParameters` within the deployment bounds. While rotation is off it alone may also call `installOperator(candidate, adminKey, launchDigest, configHash)`, the fallback for a failed operator whose key is gone, seating the named operator in effect at once, behind the timelock's delay; `OperatorInstalled` reports it, and the engine mirrors it from protocol V48. It reverts with `RotationActive` while rotation is on, and with a schedule `TurnsPending(until)` until every drawn turn has ended.
- Without a schedule (with one it reverts `ScheduleNamesTurns`), while rotation is on and the vault has had no checkpoint for `parameters.livenessTimeout`, anyone may call `promote`, which reverts with `NoQualifiedStandby` when no eligible candidate other than the operator in effect exists, leaving the operator unchanged. The promotion is the pending election for the eligible candidate with the most votes (the earlier registration on a tie), effective seven days plus the finality margin out, emitting the same `Elected` event a close does, so the engine mirrors it as an election; the vault's current release is the pending-or-current operator's from that moment. The timelock calls `setVault` once after deployment so the liveness clock is the vault's own `lastCheckpointAt`. A candidate updates its registered enclave address with `setEnclave`, which the timelock-gated `setSigner` installs while rotation is on: the vault reads the pending-or-current operator's candidate's enclave, reverting `NotTheRegisteredEnclave` for any other address. A standby that takes over with fresh keys registers them this way before the timelock installs them.

The engine mirrors `RotationChanged` and `Elected` from protocol V37 on the staking pipeline, and `OperatorInstalled` from `V48`. `RegistryLens.sol` is a stateless, read-only view over a registry, deployed beside it at any time and outside custody: `overview()` returns the switch, the parameters, the open epoch, total stake and the named, in-effect and pending operators, and `candidates(start, limit)` pages the listed candidates with their registration, votes, eligibility and role (`Candidate`, `Elected` or `Operator`). One call for all 100 costs about 4M gas; the node reads it in pages of 25 for `GET /v1/operators`. `RegistryLens.t.sol` runs it at 100 candidates against the registry's own getters. `OperatorRegistry.t.sol` covers candidacy, approvals, the close's rule and its boundaries, the switch and cancellation, and the timelock-only installation; `ReleaseChange.t.sol` covers release moves, the operator's upgrade through the vault, and how moves and installations meet; `OperatorRegistryInvariant.t.sol` checks vote and stake accounting, locked self-bonds, that only elections made while rotation is on move the role, that releases move only to approved ones and never for either side of a waiting election, that listing follows the approval of the release a candidacy holds, and that an elected operator runs its candidacy's release.

## Checkpoints and approval proofs

`postCheckpoint` retains the #24 digest and ABI: `keccak256("engine.checkpoint.v2" || uint64(chainId) || vault || uint64(seq) || root || bool(hasParent) || uint64(parentSeq) || parentRoot)`, using packed, big-endian integers. A checkpoint must increase sequence and name the exact latest accepted parent. Only one competing child can commit; stale-parent signatures cannot be relabeled with another parent.

`checkpointRoots(seq)` and `hasCheckpointAt(seq)` retain every accepted root. Claims can use older roots, which protects approvals still unpaid after later checkpoints remove or change their leaves. Roots rejected by the parent fence never become claimable. Storage grows by a bounded number of words per posted checkpoint; history has no eviction because there is no on-chain authority for deciding that every approval in a root is paid.

`checkpointSignerAt(seq)` and `checkpointEpochAt(seq)` record the signer and epoch when that exact checkpoint was accepted, and remain unchanged by later rotations. `totalWithdrawn()` counts cumulative USDC base units successfully paid; it changes atomically with the nonce, transfer and payment event, and never increases on a reverted claim. Checkpoint RPC reconciliation reads these fields at one canonical finalized block with the token balance and nonce-use status.

An approval key is `keccak256(abi.encodePacked(uint8(32), address account, uint64 nonce))`. Its value hash is `keccak256(abi.encode(address account, uint256 amountUsdc, uint64 nonce, uint64 approvedSeq))`. The compressed sparse Merkle tree hashes leaves as `keccak256(0x00 || key || valueHash)` and branches as `keccak256(0x01 || left || right)`. Siblings are supplied root-to-leaf, at most 256, and folded backwards with the key's bits from most significant to least significant. A single-leaf root takes an empty proof. Claims require an accepted checkpoint sequence at least as large as `approvedSeq`.

## Log heads

`LogHeads.sol` takes the enclave's newest released `(seq, link)` — where `link` is the cumulative
command-prefix digest, a running hash over every command's sealed bytes that checkpoints do not
reset, so a posted head commits to the whole history — under an `engine.log-head.v1` signature:
`keccak256("engine.log-head.v1" ‖ uint64(chainId) ‖ vault ‖ uint64(epoch) ‖ uint64(seq) ‖ link ‖
uint64(parentSeq) ‖ parentLink)`, packed. `post` is permissionless to relay; the recovered signer
must be the vault's current `checkpointSigner`, and the digest binds the vault's current
`signerEpoch`, so a rotation moves posts to a new epoch key. Every post names its parent — the
previously accepted head of the same epoch — and the contract requires an exact match against the
head it holds (`NotParent`) plus a strictly greater seq (`NotNewer`), so a longer divergent copy
cannot overwrite the anchor without extending it; the first post of an epoch carries no parent and
any seq. A node restarting from a log that does not reproduce the posted head refuses to start, so
a truncation older than the posting interval plus inclusion cannot resume unnoticed. The contract
has no admin: the vault reference is immutable, and a new vault deployment pairs with a new
LogHeads. `LogHeads.t.sol` covers the signature vector, newest-per-epoch, the parent fence, fuzzed
stale and replayed seqs, a forged signer and modified fields, another vault or chain, rotation
into a new epoch, and a vault without a registry refusing v2 heads.

`post` takes v1 heads only while no turn of the vault's registry's schedule names the operator
(`UseV2` otherwise; a vault without a registry has no turn). While a turn names it, `postV2` takes
`engine.log-head.v2` heartbeats (`UseV1` otherwise): `keccak256("engine.log-head.v2" ‖ uint64(chainId)
‖ vault ‖ uint64(epoch) ‖ uint64(seq) ‖ link ‖ uint64(parentSeq) ‖ parentLink ‖ uint64(turn) ‖
uint16(position) ‖ release ‖ uint64(generation) ‖ uint64(stamp) ‖ uint64(signedAt) ‖ uint8(hold) ‖
confirmer ‖ uint64(blockNumber) ‖ blockHash)`, packed, 261 bytes. A v2 head names the assignment whose
keys its enclave holds (`turn`, `position`), its release and the assignment's generation, the stamp at
`seq` and its signing time (both in milliseconds), the hold it was signed under (0 live, 1 a
benchmark-sync hold, 2 a trusted-time halt, `InvalidHold` otherwise), and the member that confirmed
holding the log through `seq`, which the contract binds but does not check. It chains as v1 does. A
live head's `signedAt` must be newer than the held head's (`SigningTimeNotNewer`) and within the
schedule's `headTolerance` of the block time either way (`SigningTimeOutsideTolerance`). A held head
instead binds an Arbitrum block (`ArbSys` at `0x64`): among the last `headBlocks` before the current
one (`BlockOutsideWindow`), with its hash (`BlockHashMismatch`), newer than the block the held head
bound (`BlockNotNewer`), and no older than the block that marked the schedule's latest marked slot
(`BlockBeforeMark`), so a host cannot release a cached held head to reset a count that witnesses are
advancing, however fast or slowly blocks come; a held head may repeat the seq and link it extends. The
signature, not the sender, is the authority, so a relayed head counts for its enclave. `heads(epoch)`
returns `(seq, link, signedAt, boundBlock, postedAt)`: the signing time (zero for v1), the bound block
(zero but for a held head) and the block time of the post. The first head, live or held, whose turn is
the turn in effect, whose position and generation are that turn's current ones, and whose release is
the one the registry names for its member, latches the assignment once, in `latches(turn, position)`:
the block time, signer epoch, member, release and generation, never overwritten; a head binding a
superseded assignment is still a heartbeat but latches nothing. `HeadPostedV2` and `TurnLatched`
report them. `LogHeadsV2.t.sol` covers the version switch both ways, the v2 known-answer vector, each
window and block rule at its edges, a cached held head refused after a burst of blocks and slow
production, repeated seqs, a relayed head, every bound field, and latches: the first head, later heads,
superseded and earlier-generation assignments, a held first head, and consecutive turns of one member.

## Withdrawal authorization

The domain is `EIP712Domain(string name,string version,uint256 chainId,address verifyingContract)`, with name `EngineWithdrawal`, version `1`, the current chain id and this Vault address. OZ `EIP712` builds the domain separator. The exact typed struct is:

```text
Withdrawal(address account,uint256 amount,uint64 nonce,uint64 approvedSeq,uint64 signerEpoch,uint64 issuedAt,uint64 expiresAt)
```

`withdraw(Withdrawal withdrawal, uint64 checkpointSeq, bytes32[] siblings, bytes signature)` is permissionless to relay and always transfers to `withdrawal.account`. `withdrawalDigest` exposes the EIP-712 digest. The signature must recover the current enclave signer using OZ ECDSA, and its epoch must equal the current epoch. `issuedAt` and `expiresAt` are Unix seconds; expiry is exactly 86400 seconds after issue, issue cannot be in the future, and expiry must be strictly after the claim's block timestamp.

An account/nonce pair can pay once across checkpoints, reissues and signer epochs. `usedNonces(account, nonce)` exposes payment status. Amounts are integer USDC base units without conversion or rounding; zero amounts, the zero account and the Vault as recipient are rejected. All entry points that transfer tokens are non-reentrant. A claim consumes its nonce before `SafeERC20` transfer, and checks both the vault debit and recipient credit equal the approved amount. A failed, fee-bearing or otherwise inexact outgoing transfer reverts atomically, preserving funds and the nonce. `WithdrawalPaid(account, amount, nonce, approvedSeq)` gives node reconciliation the full approval identity.

## MONKEY and USDC claims

`claimEmissions(address account, uint256 entitled, uint64 checkpointSeq, bytes32[] siblings)` and `claimDistribution(address account, uint256 entitled, uint64 checkpointSeq, bytes32[] siblings)` are permissionless to relay and always pay `account`. Each proves the account's cumulative amount (key `keccak256(abi.encodePacked(uint8(8), account))` for an entitlement and `uint8(13)` for a distribution, value `keccak256(abi.encode(entitled))`) against `checkpointRoots(checkpointSeq)`, and pays what it adds to `emissionsClaimed(account)` or `distributionsClaimed(account)`, reverting with `NothingToClaim` when it adds nothing. So a proof stays good while later checkpoints post, and a trader's wallet can take its time.

The checkpoint must be recorded (`UnknownCheckpoint`) in the signer epoch in force (`InvalidSignerEpoch`), and the signer must not be retired (`NoSigner`): a rotation or a guardian's retirement ends the claims on every earlier root, for good. The next signer's first checkpoint proves at least as much, and the vault pays it less what was already paid, so nothing is lost while one can still post. Once the exit has started none can: USDC is then registered against the exit root, and MONKEY not yet minted when its signer was replaced or retired stays unminted.

An older root cannot overpay, because each amount only grows: the engine adds to an entitlement when an emission period closes and to a distribution when a staking epoch closes, and nothing reduces either, a reversed deposit included, which becomes an emission debt against later weight. `entitled` at an older root is therefore at most what the newest root holds, the vault pays no more than was due at that root, and a later root pays the rest. Each USDC payment counts in `distributionsPaid`, which node reconciliation adds to the vault's balance and compares with what the engine allocated by the checkpoint the vault last recorded, so it holds whichever root a claim names.

## Exit against the last posted root

`lastCheckpointAt()` is the block time of the latest accepted checkpoint, or of deployment before the first. Once `checkpointsStale()`, `staleAfter` seconds after it, every deposit route and `bookSurplus` revert with `CheckpointsStale` until a checkpoint is posted. Once `exitPeriod` seconds have passed, anyone may call `startExit(terms, siblings)`, which proves the root's exit terms leaf (key `keccak256(abi.encodePacked(uint8(24)))`, value `keccak256(abi.encode(uint64 depositCursor, int128 pending, int128 held, int128 unheld, uint64[] gaps))`) against `latestRoot`, or, with no checkpoint ever posted, takes a cursor of zero. Every deposit id at or past the cursor is refunded; `gaps` lists the lowest 64 ids below it the root does not hold, which only a reorganisation the engine was still applying leaves, and the vault refunds them too, marking them in `exitRefundableGap`. `unheld` commits the principal of every id below the cursor the root does not hold, the named gaps included: the reserve holds it, and whatever no gap names stays in the vault rather than reaching the pools. The exit is permanent: `postCheckpoint`, `withdraw` and `claimDistribution` revert with `ExitActive`, and deposits stay refused. Neither pause nor the signer epoch applies to anything below. `claimEmissions` stays open under its own rule, on any recorded root of the signer epoch in force while the signer is not retired, and pays no USDC.

The vault records each deposit's payer and amount (`depositRecords(id)`), and `refundableThrough(id)` the running total of payer-funded deposits, booked surpluses aside. At the start, the exit reserves every payer-funded deposit from the cursor on that the root does not hold, and the root's pending principal rounded up, in `exitRefundReserve`, and the held principal rounded up in `exitHeldReserve`, which it never pays. A cursor past the vault's deposit count is taken as that count. `refundDeposit(id)` pays a deposit from the cursor on that the root does not hold back to its payer, and `refundPendingDeposit(chainRef, pending, siblings)` one the root holds pending (key `keccak256(abi.encodePacked(uint8(34), chainRef))`, value `keccak256(abi.encode(uint64 depositId, address account, address payer, int128 amount))`) whose vault record has the same payer and amount; each deposit is refunded once, at any time after the start, from the reserve.

For `claimWindow` seconds after the start, anyone may register for an account, each once: `registerExit` its equity at the root's marks, through `ExitVerifier.accountClaim`, which proves the account leaf, exactly its `openPositions` position leaves in strictly increasing markets, and each one's market leaf, values each position's `(mark - entry) * qty` rounded down and converted to USD at the market's FX mark rounded down, and floors the sum with the balance at zero, in whole base units rounded down; `registerExitWithdrawal` an approval leaf whose nonce is unused, which it then marks used; `registerExitQueued` a queued request's remainder (value `keccak256(abi.encode(address account, int128 amount, int128 remaining, uint64 requestedSeq, uint64 ticket))`); and `registerExitDistribution` the part of a distribution leaf not already claimed. After the window, the first `claimExit` or `releaseHouseRemainder` fixes the pools: what the vault holds beyond both reserves goes to client claims, up to their total, then to distribution claims, up to theirs, and the rest is `houseRemainder`. `claimExit(account)` pays an account its claims times each pool over that pool's total, rounded down, once; `releaseHouseRemainder(to)`, callable only through the timelock, pays the remainder once.

`ExitVerifier`, which the vault deploys, holds no state; the vault compiles within EIP-170's size limit only with the optimizer, which `foundry.toml` enables. `StateTree` is the shared proof check.

## Daily turn seeds

`SeedSchedule.sol` fixes which beacon epoch's RANDAO mix seeds each daily operator turn: turn `n` starts at 22:30 UTC on day `n` of the Unix epoch, its draw deadline is a day earlier, and its seed is the mix at the end of the epoch holding the time two days before the deadline, counted from the beacon genesis time each contract is deployed with (`seedEpoch`, `drawDeadline`). Consecutive turns' epochs are 225 apart.

`SeedRelay.sol` on Ethereum proves a turn's mix and sends it to the receiver as an Arbitrum retryable ticket that `msg.value` pays. `relay(turn, witness, fees)` takes an execution block's time, whose EIP-4788 entry is the witness header's root; the header; the state's `fork.current_version` with its 8-sibling branch; and the seed with its 22-sibling branch to `randao_mixes[epoch % 65536]`. It refuses a turn past its draw deadline, a root EIP-4788 no longer holds (it keeps about 27 hours), a header that does not hash to it, a state not past the epoch or past the slot at which the mix's index is reused, a fork version it was not deployed with, and a branch that does not verify. Each branch is checked with the consensus specification's `is_valid_merkle_branch` over the SHA-256 precompile. The ticket refunds unspent fees to the caller on Arbitrum, and its beneficiary is the receiver, which cannot cancel it, so a ticket whose redemption fails stays redeemable by anyone. Anyone may relay, and a turn may be relayed again; only the first delivery counts.

`SeedReceiver.sol` on Arbitrum records a seed only from the relay's address with Arbitrum's L1-to-L2 alias applied, only for the epoch the schedule fixes for its turn, and only before the turn's draw deadline. `seedOf(turn)` answers from the deadline on: the relayed seed, or `keccak256(abi.encode(s, turn))`, where `s` is the seed of the latest earlier turn that has one; it refuses before any turn has a seed. Neither contract has an admin.

Deploy the receiver on Arbitrum naming the relay's address before the relay exists, from the deployer's next nonce on Ethereum, then the relay with the receiver's address, both with the network's beacon genesis time (`1606824023` on mainnet); check that the relay landed at the address the receiver names. The relay takes the fork versions whose states it reads, each one whose `BeaconState` keeps the Electra-onward layout, its fields filling a 64-leaf tree: on mainnet, `0x05000000` (Electra) and `0x06000000` (Fulu). A later fork needs a node release whose relayer reads its state, and, unless its version was listed here because its specification keeps the layout, a new pair. The operator schedule reads its seeds from the receiver in the launch deployment.

## Daily operator turns

`OperatorSchedule.sol` names the operator by daily turns for a registry that names it. Deploy it with the registry and the seed receiver; the timelock then calls the registry's `setSchedule` once, while rotation is off, with a schedule built for that registry (`InvalidSchedule` otherwise, `ScheduleAlreadySet` for a second call), which `ScheduleSet` reports. From then on a close never elects and `promote` reverts `ScheduleNamesTurns`; a registry without a schedule elects as above. While a schedule is named the epoch lasts at least `MIN_SCHEDULED_EPOCH`, one day: `setSchedule` and `setParameters` refuse a shorter one with `EpochTooShort(epochLength, minimum)`.

- Rotation sets: while rotation is on, every close adopts a rotation set in the schedule, effective seven days plus the finality margin after the close, or when the set adopted before it takes effect if that is later, so sets take effect in the order adopted; `RotationSetAdopted(setId, epoch, effectiveAt, quorum, candidates, adminKeys, weights)` reports it with that time. Sets waiting to take effect queue: a close never waits for an earlier set, and each takes effect after its own notice. With a quorum the set is every eligible listed candidate with votes, weighted by its votes. Without one it is the latest adopted set, waiting or not, less the members no longer eligible or registered since under another admin key, their weights unchanged. A set holds each member's admin key as adopted. A set holds at most `CANDIDATE_LIMIT` plus one members, 101: it is drawn from the registry's list, which the named operator's place beyond the cap bounds there. When the result is empty the close adopts an empty set if the latest adopted set has members, so a set whose members all lapsed is replaced rather than kept, and nothing otherwise. Each close ends an epoch at least one epoch length after the last close's, and only a close called late lets the next follow at once, so with the epoch length held at one day or more, at most ⌈(7 days + finality margin) / 1 day⌉ + 1 sets wait at once, counting the largest finality margin in force over that time: 9 with a margin up to a day. Each change of the epoch length by the timelock can let one more close follow at once. `currentSetId()` and `setAt(timestamp)` are the latest set whose effective time has come, `pendingSetId()` the earliest still waiting, zero when none waits; all move at the effective times without a transaction, and `setOf(setId)` returns a set's epoch, effective time, members and weights.
- Draws: anyone calls `draw(turn)` from the turn's draw deadline, a day before its 22:30 UTC boundary, until that boundary (`NotDrawable(turn, opensAt, closesAt)` outside it), while the registry's `rotationSwitch` is on (`RotationOff`), once (`AlreadyDrawn`), from the set in effect at the turn's draw deadline, so the moment of the draw within its window cannot choose between two sets (`NoSetInEffect` before any, `EmptySet(setId)` for an empty one, after which the last member stays named). Position by position from zero, `memberAt` picks the member whose cumulative weight first exceeds `keccak256(abi.encode(seed, turn, position))` modulo the set's total weight, with replacement, so a later position may repeat an earlier member; the first member the registry still lists (`isListed`) under the admin key the set adopted (`keyHolder`) takes the turn. After 64 weighted positions without one, the scan's positions follow, one for each member: position `64 + k` is the member `k` places after the one at index `keccak256(abi.encode(seed, turn, 64))` modulo the member count, wrapping, so a turn reverts `NoAvailableMember` only when no member is available, and its position, at most 164, tells a scan pick from a weighted one. The seed and the set are fixed at the draw deadline, but availability is read at the draw: a deregistration or a withdrawn approval landing within the day-long window lets whoever draws choose by drawing before or after it. `TurnAssigned(turn, setId, position, reason, candidate, adminKey, release, generation)` reports the turn with the admin key the set adopted and the member's release at the draw; `reason` is 0 for a draw.
- Seeds: a turn's seed is `seedReceiver.seedOf(turn)`. Only the receiver's `NoRelayedSeed` refusal falls back, to `keccak256(abi.encode(seedAnchor, turn))`; any other failure of the read, running out of gas included, reverts the draw, so a caller cannot choose the fallback by limiting gas. An Ethereum fork needs a new relay and receiver: the timelock names the receiver with the schedule's `setSeedReceiver`, which `SeedReceiverChanged` reports and which fixes `seedAnchor()` as the last drawn turn's seed at that moment, and turns draw from the fallback until the new receiver has a relayed seed. Since the anchor is fixed at the change, drawing or skipping one turn leaves every later turn's fallback seed unchanged. A receiver replaced before any draw leaves no anchor, and the fallback refuses with `NoSeed`.
- Naming: a turn names its member from its boundary for a day (`turnOf`, `turnAt`, `namedAt`), and the last drawn turn keeps naming its member after it ends until another turn starts. The registry's `namedOperator`, `operatorInEffect`, `operatorRelease` and `operatorEnclave` read the member's candidacy as it is now, so a member's `setRelease` moves the release the vault names at once, and `setSigner` installs only the member's registered enclave. Turning rotation off stops draws and adoptions, but drawn turns stand: the registry's `rotationEnabled()` stays true while a turn names the operator, so the vault keeps following it, `setCurrentRelease` reverts, and `installOperator` reverts `TurnsPending(until)` until `turnsRunUntil()`; the installation then ends the last turn's naming. Each turn records its source, the operator the registry named at its draw, which hands its member the keys (`sourceOf(turn)`): the previous turn's member, or, for the first turn and the first after an installation, the operator named before the turns. While a turn names the operator or a drawn turn runs, a member cannot deregister while it has held any assignment of the turn in effect or of the last drawn turn, or is the turn in effect's source (`holdsTurn`); once an installation past the last turn's end names another operator, it may leave.
- Assignments: every assignment of a turn is kept by `(turn, position)` and never erased: `assignmentOf(turn, position)` returns its member, the admin key its set adopted, the set, the reason (0 a draw, 2 a promotion), and for a promotion the standby key, the signer epoch, the outgoing epoch's latest head and the vault's latest accepted checkpoint it fixed, with the block time it was made; and its revisions, the release and generation it was made with and each one a release move gave it after. `turnOf(turn)` follows the latest assignment's member, position, reason and generation, and keeps the draw's set, prior turn, seed and source, so `turnAt`, `namedAt`, the registry and the vault follow a promotion at once. `heldTurn(turn, candidate)` records every member that held an assignment of a turn.
- Generations: the vault hands out every generation from one counter, `generationCounter()`: each `setCurrentRelease`, each `syncRelease` that folds a change, and each `reserveGeneration`, which only the registry's schedule may call (`UnauthorizedSchedule`). A draw continues the holding of the operator the registry names when it runs: when the member drawn is that operator, on the release the registry names for it, and the vault has that release folded (`syncedRelease()`), the turn keeps the vault's `releaseGeneration()`. So the incumbent's first turn keeps its fold's generation, a member drawn for the next turn keeps its own, and so does a member drawn again after an undrawn day, since it stays named across the gap. Any other draw reserves a new generation: another member, even on the same release, and a member drawn after an installation named another operator in between. A member's `setRelease` gives the turn in effect and the last drawn turn whose latest assignment it holds one new generation, shared, which `TurnGenerationMoved(turn, generation)` reports for each and each assignment records as a revision. While a turn names the operator, `releaseGeneration()` is the turn's, `syncedRelease()` is `currentRelease()`, and `syncRelease` is a no-op. Otherwise both are the vault's last fold, which a draw does not move before the turn's boundary; once a turn has named the operator since that fold, `syncedRelease()` reads zero until `syncRelease` or `setCurrentRelease` folds a new generation, so no copy sealed before the turns reopens.

- Liveness: the schedule is deployed with its `LogHeads`, the heartbeat rule `liveness()` — `heartbeatInterval` (60 s by default), `headTolerance`, `heartbeatMisses` (5 by default) and `headBlocks` — the rule's bounds `livenessMinimums()` and `livenessMaximums()`, and the immutable `switchBudget()` (the handover's asserted switch budget, in seconds) and `blockMillis()` (the pinned Arbitrum block time). The constructor and `setLiveness` refuse a rule outside its bounds or breaking `heartbeatMisses >= 2`, `(heartbeatMisses + 1) * heartbeatInterval + headTolerance <= 600`, `headTolerance < heartbeatInterval`, `headBlocks <= 256`, `headBlocks * blockMillis < heartbeatInterval * 1000` or `heartbeatMisses * heartbeatInterval > switchBudget` (`InvalidLiveness`). Only the registry's timelock calls `setLiveness` (`UnauthorizedGovernance`), only while no turn names the operator (`TurnNamesTheOperator`), so no count runs across a change; `LivenessChanged` reports it. Slot `k` is `[k * heartbeatInterval, (k + 1) * heartbeatInterval)` of block time. While a turn names the operator (`NoTurn` otherwise), anyone may `witness()`, which marks the current slot once with its block time and Arbitrum block (`marks(slot)`, `latestMark()`, `SlotWitnessed`); a repeated witness returns false and changes nothing, no other slot is ever marked, and a mark counts for slot `k` only while its time divided by the interval in force is `k`, so a mark made under another interval never counts.
- Promotion: `promote()` is permissionless once the `heartbeatMisses` complete slots before the current one are all marked and all after `s`, the later of the slots of the signer epoch's latest head (`LogHeads.heads(epoch).postedAt`) and of the vault's `signerSince()`: an unmarked slot, as in a chain outage, restarts the count, a head in the same block before it refuses it (`PromotionNotDue(dueAt)`), one after it fails as the old epoch's, and every signer change restarts the count. `promotionDueAt()` gives the earliest block time the count could pass assuming every later slot is marked, `(max(s, u) + heartbeatMisses + 1) * heartbeatInterval` with `u` the latest unmarked slot after `s` among the `heartbeatMisses` before the current one, a time at or before now while it passes, and `type(uint64).max` while no turn names the operator. It names the first position after the turn's current assignment, in `memberAt`'s order up to the scan's end, whose member the registry lists under the admin key its set adopted, holds a promotable standby key and has held no assignment of the turn, so positions only advance and no member is retried (`NoQualifiedPosition(turn)` when none is left). In one transaction it reserves a new generation, records the assignment with the commitments above, moves `turnOf`, consumes the standby record (`StandbyConsumed`), emits `TurnAssigned` with reason 2 and `Promoted`, and calls the vault's `promoteSigner`, which refuses a started exit or a retired signer. While no turn names the operator it reverts `NoTurn`. Order exhaustion leaves the governance fallback: rotation off, then `installOperator` once drawn turns end.
- Standby keys: a registered candidate whose release the timelock approved calls `registerStandby(key, nonce, expiry, vouch)`, where `vouch` signs, with no message prefix, `vouchDigest(candidate, key, release, nonce, expiry)` = `keccak256(abi.encode(keccak256("engine.standby-vouch.v1"), chainId, vault, registry, schedule, candidate, key, release, nonce, expiry))` for the candidate's current release, by the vault's current signer or any candidate's promotable standby key, so the operator in effect cannot keep a candidate out (`InvalidVouch`, `VouchExpired`, `NotRegistered`, `ReleaseNotApproved`). A key registers once ever and never after it was the vault's signer (`InvalidStandbyKey`); a new registration replaces the candidate's record and voids the old key (`standbyOf`, `standbyHolder`, `StandbyRegistered`). `promotable(candidate)` is the record's key while the candidate runs the release it was registered for, that release is approved for it, no promotion consumed it and it was never the signer, so `setRelease` or a withdrawn approval voids it. The registry's `register` and `setEnclave` refuse a registered standby key as an enclave (`EnclaveIsStandbyKey`), and a close leaves out of the set a candidate with no promotable standby key, while its votes still count toward the quorum.

## Parameter votes

`ParameterVote.sol` carries the votes that change the engine's governed parameters while the registry's `rotationEnabled()` holds. It is deployed with the operator schedule, whose registry it reads, and a normal and a fast window of one second to 30 days each. A member of the rotation set in effect, a candidate address `setOf` lists, calls `propose(command, fast)` with 1 to 32,768 command bytes, which casts its own yes vote; members of that same set call `vote(id)` until the path's window closes, each with the weight the set adopted, so later stake moves and later sets change nothing. The vote that first takes the yes weight past two thirds of the set's total (`passes`: `3 * yes > 2 * total`, so exactly two thirds fails) emits `ProposalPassed` once, with the command's bytes and hash; a member that does not vote counts against. The engine mirrors `ProposalPassed` from finalised blocks from protocol V56 and holds every change to its own limits, applying the fast path, without notice, only to risk-reducing restrictions; the contract reads no command, carries no limits, holds no funds and has no admin. At 101 members a proposal of the longest command costs about 24.5M gas and the vote that passes it about 3.4M. `ParameterVote.t.sol` covers the constructor's bounds, the two-thirds boundary, each path's window to its last second, the set a proposal keeps when a newer one takes effect, every refusal and paging, and fuzzes `passes` and random subsets of a set voting; `ParameterVoteInvariant.t.sol` mixes proposals, votes, new sets, switches and time, and checks that the yes weight is the votes cast within the set's total, that a proposal has passed exactly when past two thirds with one `ProposalPassed`, that each command hashes to its `commandHash`, and that no vote counts from the close.
