# Custody vault

`Vault.sol` holds six-decimal USDC collateral on Arbitrum One. The deterministic engine owns trading balances and the FIFO withdrawal queue. The vault accepts deposits, stores enclave-signed checkpoints, and pays signed approvals proven against an accepted checkpoint. It is not upgradeable. Emergency exits remain separately scoped in #48.

Deposits accept 10 to 1e9 USDC per call. `deposit`, `depositFor` and `depositToHouse` share one deposit-id sequence. The events report the tokens actually received, including for a token with an incoming transfer fee. The engine credits finalized events once by transaction hash and log index.

`totalDeposited()` counts the USDC base units every deposit brought in, and `depositedThrough(id)` holds that total just after deposit `id`, so the node compares its ledger with exactly the deposits it has credited while later ones are still in flight. USDC that reaches the vault outside a deposit, such as a direct transfer, is a surplus: the token balance plus `totalWithdrawn()` and `distributionsPaid()` exceeds `totalDeposited()`. A surplus does not pause withdrawals; the node raises a Warning until it is booked. Anyone may call `bookSurplus()` to record it as a house deposit, a `HouseDeposited` event from the caller in the same id sequence, at most 1e9 USDC per call. A surplus below the 10 USDC minimum reverts with `NoSurplus` and must be topped up first.

## Governance and deployment

Deploy an [OpenZeppelin `TimelockController`](https://docs.openzeppelin.com/contracts/5.x/api/governance#TimelockController) with a deployment-selected, nonzero minimum delay and the deployment's multisig as proposer. Configure executor and administrator roles deliberately; the timelock must administer itself after setup. Pass that deployed timelock as the third Vault constructor argument, after the token and attestation-verified enclave signer, the multisig's own address as the fourth, the guardian, and the engine's initial MONKEY emission period budget as the fifth, which caps the MONKEY token the vault deploys and alone mints. The Vault constructor checks that the timelock has code and a nonzero delay. Deployment must verify the supplied contract is the intended OZ implementation and that its roles belong to the intended multisig; a Solidity address/type cannot establish those facts.

Only calls executed by the timelock may invoke `setSigner(address)`, `setCurrentRelease(bytes launchDigest, bytes32 configHash)`, or `setPauses(bool depositsPaused, bool withdrawalsPaused)`; the guardian is not the timelock and cannot call them. `setCurrentRelease` records `currentRelease = keccak256(launchDigest ‖ configHash)`: the one enclave release, a 48-byte SEV-SNP launch measurement running the config file with that SHA-256, that may hold the enclave's keys. Nodes read it at custody finality: a node opens or seals keys only while it names the node's own release, and the running release hands its keys only to the release it names, so setting a new one supersedes the old. Every call raises `releaseGeneration`, even for a release named before or the current one: a node seals its keys under the generation it runs in and opens only a copy sealed under the current one, so a release named again takes the keys afresh from the running release instead of reopening an older copy. It changes no signer or epoch, so outstanding authorizations stay valid across an upgrade or config change, and `CurrentReleaseChanged` records each change with its generation, measurement and config hash. A launch digest of any other length reverts with `InvalidLaunchDigest`. Signer changes increment `signerEpoch`, initially 1, including when the same address is reused. Both checkpoint and withdrawal verification use the current `checkpointSigner`. Rotation immediately invalidates old withdrawal epochs; current-key reissues retain the original account, amount, nonce and approval sequence. The nonce-use mapping survives rotation. `signerAtEpoch(epoch)` preserves each assigned epoch's signer for replay authentication, including epochs with no checkpoint, while claims and checkpoints still require the current signer. `SignerChanged` and `PausesChanged` record administration.

Deposit pause covers every deposit route, including house capital and `bookSurplus`. Withdrawal pause blocks withdrawal and distribution claims without consuming nonces. The flags are independent; checkpoint posting remains available during either pause. Changing either flag requires the configured timelock delay.

The guardian, an immutable address set at deployment to the multisig, acts at once, without the delay, in an emergency such as a possibly compromised enclave signer. It can do two things and nothing else. `pauseWithdrawals()` pauses withdrawal and distribution claims for `GUARDIAN_PAUSE`, seven days, emits `GuardianPausedWithdrawals(until, pauses)` and increments the public `guardianPauses()` counter; it reverts while withdrawals are already paused, so the guardian cannot extend a pause in force. The timelock renews a pause by pausing withdrawals itself, which holds until it unpauses, and its `setPauses` with withdrawals unpaused also ends a guardian pause early. `withdrawalsPausedUntil()` is the end of the current pause, `type(uint256).max` for the timelock's. `retireSigner()` clears `checkpointSigner` and emits `SignerRetired(signer, signerEpoch)`: no withdrawal signed in the current epoch and no checkpoint is accepted again, and the retirement never expires; `setSigner` through the timelock then starts the next epoch. Retiring leaves `signerEpoch` and `signerAtEpoch` unchanged and reverts with `NoSigner` once retired. A retired signer does not stop distribution claims against the last posted root: once a guardian pause ends they resume unless the timelock has renewed it. Deposits, `bookSurplus` and emission claims are unaffected by either. Timelock delay/role changes themselves follow OZ governance; the deployment must preserve its intended delay and proposer policy.

This change requires a new Vault deployment and constructor updates in deployment clients. It provides no migration of an existing Vault's balances, accepted roots or used nonces. The signing node must read the current signer epoch and reconcile against the deployed Vault before releasing authorizations.

## Staking and the operator election

`Staking.sol` holds staked MONKEY, enforces the unstake cooldown, and emits `Staked`, `UnstakeStarted` and `UnstakeCompleted`. A staker delegates its whole stake to one candidate with `delegate(candidate)`, changes it at any time, and clears it with the zero address, which abstains. `votes(candidate)` follows `stakes`: it rises at `stake` and drops at `startUnstake`, though the unstaking amount keeps earning distributions through the cooldown, and `totalStaked()` excludes unstaking amounts. Delegation changes nothing about distributions.

`OperatorRegistry.sol` elects the operator whose key signs the engine's admin commands. Its constructor deploys `Staking`, which records the registry as the only caller of `lockBond` and `releaseBond`; deploy `Staking` only this way. The constructor takes the MONKEY token, the staking cooldown and distribution epoch, the timelock, the initial operator in effect (its admin key, 48-byte launch measurement, and config hash), and the election parameters with the lowest and highest value of each. The parameters are the epoch length, the minimum term, the finality margin, the challenger's margin in basis points of the incumbent's votes, the eligibility share and quorum in basis points of total stake, the candidate cap (at most `CANDIDATE_LIMIT`, 100, which bounds a close's gas), and the minimum self-bond. Their production values and bounds are not set here.

- `register` records the caller's admin key, self-bond, API hostname, handover endpoint and release, `keccak256(launchDigest ‖ configHash)` as the vault names a release, and locks the self-bond in `Staking`; `startUnstake` cannot take it while the candidate is registered nor for one cooldown after `deregister`. Admin keys are unique among candidates. The operator in effect, and a candidate elected and waiting to take effect, cannot deregister.
- The timelock's `setReleaseApproval` approves a candidate's own release. Approval lists the candidate in `candidateList` under the candidate cap — only approved candidates count toward the cap and enter the list, so unapproved registrations cannot fill it; withdrawing approval delists the candidate while it stays registered, and a re-registration whose release is still approved relists at once.
- A candidate is eligible while it is listed, its self-bond meets the minimum, and its votes meet the eligibility share.
- Anyone calls `closeEpoch` once the open epoch has ended; unclosed epochs are skipped. While rotation is on and no election waits to take effect, the close elects the eligible candidate with the most votes, the earlier registration on a tie, when it is not the operator in effect, listed candidates' votes reach the quorum, the operator in effect has served its minimum term since it took effect, and the winner's votes exceed the incumbent's by the margin (an incumbent that is not eligible has none). `Elected` names the epoch, candidate, admin key, release, and the effective time, seven days plus the finality margin after the close. `operatorInEffect()` returns the election from that time.
- Only the timelock calls `setRotation`, off at deployment with the initial operator in effect; turning it off cancels an election not yet in effect, which `RotationChanged(false, true)` reports. It also approves releases and calls `setParameters` within the deployment bounds.

The engine mirrors `RotationChanged` and `Elected` from protocol V37 on the staking pipeline. `OperatorRegistry.t.sol` covers candidacy, approvals, the close's rule and its boundaries, the switch and cancellation; `OperatorRegistryInvariant.t.sol` checks vote and stake accounting, locked self-bonds, and that only elections made while rotation is on move the role.

## Checkpoints and approval proofs

`postCheckpoint` retains the #24 digest and ABI: `keccak256("engine.checkpoint.v2" || uint64(chainId) || vault || uint64(seq) || root || bool(hasParent) || uint64(parentSeq) || parentRoot)`, using packed, big-endian integers. A checkpoint must increase sequence and name the exact latest accepted parent. Only one competing child can commit; stale-parent signatures cannot be relabeled with another parent.

`checkpointRoots(seq)` and `hasCheckpointAt(seq)` retain every accepted root. Claims can use older roots, which protects approvals still unpaid after later checkpoints remove or change their leaves. Roots rejected by the parent fence never become claimable. Storage grows by a bounded number of words per posted checkpoint; history has no eviction because there is no on-chain authority for deciding that every approval in a root is paid.

`checkpointSignerAt(seq)` and `checkpointEpochAt(seq)` record the signer and epoch when that exact checkpoint was accepted, and remain unchanged by later rotations. `totalWithdrawn()` counts cumulative USDC base units successfully paid; it changes atomically with the nonce, transfer and payment event, and never increases on a reverted claim. Checkpoint RPC reconciliation reads these fields at one canonical finalized block with the token balance and nonce-use status.

An approval key is `keccak256(abi.encodePacked(uint8(32), address account, uint64 nonce))`. Its value hash is `keccak256(abi.encode(address account, uint256 amountUsdc, uint64 nonce, uint64 approvedSeq))`. The compressed sparse Merkle tree hashes leaves as `keccak256(0x00 || key || valueHash)` and branches as `keccak256(0x01 || left || right)`. Siblings are supplied root-to-leaf, at most 256, and folded backwards with the key's bits from most significant to least significant. A single-leaf root takes an empty proof. Claims require an accepted checkpoint sequence at least as large as `approvedSeq`.

## Withdrawal authorization

The domain is `EIP712Domain(string name,string version,uint256 chainId,address verifyingContract)`, with name `EngineWithdrawal`, version `1`, the current chain id and this Vault address. OZ `EIP712` builds the domain separator. The exact typed struct is:

```text
Withdrawal(address account,uint256 amount,uint64 nonce,uint64 approvedSeq,uint64 signerEpoch,uint64 issuedAt,uint64 expiresAt)
```

`withdraw(Withdrawal withdrawal, uint64 checkpointSeq, bytes32[] siblings, bytes signature)` is permissionless to relay and always transfers to `withdrawal.account`. `withdrawalDigest` exposes the EIP-712 digest. The signature must recover the current enclave signer using OZ ECDSA, and its epoch must equal the current epoch. `issuedAt` and `expiresAt` are Unix seconds; expiry is exactly 86400 seconds after issue, issue cannot be in the future, and expiry must be strictly after the claim's block timestamp.

An account/nonce pair can pay once across checkpoints, reissues and signer epochs. `usedNonces(account, nonce)` exposes payment status. Amounts are integer USDC base units without conversion or rounding; zero amounts, the zero account and the Vault as recipient are rejected. All entry points that transfer tokens are non-reentrant. A claim consumes its nonce before `SafeERC20` transfer, and checks both the vault debit and recipient credit equal the approved amount. A failed, fee-bearing or otherwise inexact outgoing transfer reverts atomically, preserving funds and the nonce. `WithdrawalPaid(account, amount, nonce, approvedSeq)` gives node reconciliation the full approval identity.

## Tests and shared vector

Dependencies are pinned in `soldeer.lock`. From this directory, install with `forge soldeer install`, then run `forge fmt --check`, `forge build` and `forge test`. Foundry needs Cancun for the existing transient reentrancy guard. Its filesystem permission grants read access only to `test/fixtures`.

`test/fixtures/withdrawal.json` is the shared Rust/Solidity interoperability vector. It includes the exact domain/type, approval leaf key/value, four ordered siblings, accepted root, hashes, signer and signature. The signer is the explicitly public test key `0x1234`. This artifact is independent of immutable protocol reference logs. `WithdrawalVector.t.sol` verifies its digest, recovered signer, proof and exact payout at the fixture's chain/address. The Rust signer must consume this same artifact.

`Withdrawals.t.sol`, `WithdrawalProofs.t.sol` and `Governance.t.sol` (with release approvals) cover replay, roots and fork parents, proof/signature tampering, time/epoch boundaries, timelock access, independent pauses, fee tokens, failure rollback and reentrancy. `Guardian.t.sol` covers the guardian's immediate pause, its seven-day end, renewal and early unpause by the timelock, the refused extension, signer retirement until a new signer, and that the guardian can do nothing else. `SignerHistory.t.sol` checks reissues across repeated rotations, including epochs with no checkpoint and reused signer addresses. `WithdrawalInvariant.t.sol` mixes deposits, approvals, claims, reissues, signer rotations, timelock and guardian pauses, retirements and clock advances, checking token conservation, retained roots, exactly-once payment, the pause counter and bound, and that a retired signer stays retired until a new one. The existing deposit and checkpoint suites remain in place.
