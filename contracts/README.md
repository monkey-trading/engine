# Custody vault

`Vault.sol` holds six-decimal USDC collateral on Arbitrum One. The deterministic engine owns trading balances and the FIFO withdrawal queue. The vault accepts deposits, stores enclave-signed checkpoints, and pays signed approvals proven against an accepted checkpoint. If checkpoints stop, anyone can start its exit against the last posted root. It is not upgradeable.

Deposits accept 10 to 1e9 USDC per call. `deposit`, `depositFor` and `depositToHouse` share one deposit-id sequence. The events report the tokens actually received, including for a token with an incoming transfer fee. The engine credits finalized events once by transaction hash and log index.

`totalDeposited()` counts the USDC base units every deposit brought in, and `depositedThrough(id)` holds that total just after deposit `id`, so the node compares its ledger with exactly the deposits it has credited while later ones are still in flight. USDC that reaches the vault outside a deposit, such as a direct transfer, is a surplus: the token balance plus `totalWithdrawn()` and `distributionsPaid()` exceeds `totalDeposited()`. A surplus does not pause withdrawals; the node raises a Warning until it is booked. Anyone may call `bookSurplus()` to record it as a house deposit, a `HouseDeposited` event from the caller in the same id sequence, at most 1e9 USDC per call. A surplus below the 10 USDC minimum reverts with `NoSurplus` and must be topped up first.

## Governance and deployment

Deploy an [OpenZeppelin `TimelockController`](https://docs.openzeppelin.com/contracts/5.x/api/governance#TimelockController) with a deployment-selected, nonzero minimum delay and the deployment's multisig as proposer. Configure executor and administrator roles deliberately; the timelock must administer itself after setup. Pass that deployed timelock as the third Vault constructor argument, after the token and attestation-verified enclave signer, the multisig's own address as the fourth, the guardian, and the engine's initial MONKEY emission period budget as the fifth, which caps the MONKEY token the vault deploys and alone mints. The sixth to eighth are the exit period, the claim window and the deposit staleness, in seconds (see Exit below). The Vault constructor checks that the timelock has code and a nonzero delay, that the exit period exceeds that delay, and that the claim window and staleness are nonzero with the staleness at most the exit period. Deployment must verify the supplied contract is the intended OZ implementation and that its roles belong to the intended multisig; a Solidity address/type cannot establish those facts.

Only calls executed by the timelock may invoke `setSigner(address)`, `setCurrentRelease(bytes launchDigest, bytes32 configHash)`, or `setPauses(bool depositsPaused, bool withdrawalsPaused)`; the guardian is not the timelock and cannot call them. `setCurrentRelease` records `currentRelease = keccak256(launchDigest ‖ configHash)`: the one enclave release, a 48-byte SEV-SNP launch measurement running the config file with that SHA-256, that may hold the enclave's keys. Nodes read it at custody finality: a node opens or seals keys only while it names the node's own release, and the running release hands its keys only to the release it names, so setting a new one supersedes the old. While the vault's named registry has rotation on, `currentRelease` is instead the pending-or-current operator's release, which moves to a promoted standby at once, and `setCurrentRelease` reverts `RotationActive`; `syncRelease`, callable by anyone, folds a registry-driven release change into `releaseGeneration` so a standby seals keys only after the change is counted. Every call raises `releaseGeneration`, even for a release named before or the current one: a node seals its keys under the generation it runs in and opens only a copy sealed under the current one, so a release named again takes the keys afresh from the running release instead of reopening an older copy. It changes no signer or epoch, so outstanding authorizations stay valid across an upgrade or config change, and `CurrentReleaseChanged` records each change with its generation, measurement and config hash. A launch digest of any other length reverts with `InvalidLaunchDigest`. Signer changes increment `signerEpoch`, initially 1, including when the same address is reused. Both checkpoint and withdrawal verification use the current `checkpointSigner`. Rotation immediately invalidates old withdrawal epochs; current-key reissues retain the original account, amount, nonce and approval sequence. The nonce-use mapping survives rotation. `signerAtEpoch(epoch)` preserves each assigned epoch's signer for replay authentication, including epochs with no checkpoint, while claims and checkpoints still require the current signer. `SignerChanged` and `PausesChanged` record administration.

Deposit pause covers every deposit route, including house capital and `bookSurplus`. Withdrawal pause blocks withdrawal and distribution claims without consuming nonces. The flags are independent; checkpoint posting remains available during either pause. Changing either flag requires the configured timelock delay.

The guardian, an immutable address set at deployment to the multisig, acts at once, without the delay, in an emergency such as a possibly compromised enclave signer. It can do two things and nothing else. `pauseWithdrawals()` pauses withdrawal and distribution claims for `GUARDIAN_PAUSE`, seven days, emits `GuardianPausedWithdrawals(until, pauses)` and increments the public `guardianPauses()` counter; it reverts while withdrawals are already paused, so the guardian cannot extend a pause in force. The timelock renews a pause by pausing withdrawals itself, which holds until it unpauses, and its `setPauses` with withdrawals unpaused also ends a guardian pause early. `withdrawalsPausedUntil()` is the end of the current pause, `type(uint256).max` for the timelock's. `retireSigner()` clears `checkpointSigner` and emits `SignerRetired(signer, signerEpoch)`: no withdrawal signed in the current epoch, no checkpoint, and no MONKEY or USDC claim on a root of that epoch is accepted again, and the retirement never expires; `setSigner` through the timelock then starts the next epoch, whose first checkpoint claims prove against. Retiring leaves `signerEpoch` and `signerAtEpoch` unchanged and reverts with `NoSigner` once retired. A guardian pause alone does not stop emission claims. Deposits and `bookSurplus` are unaffected by either. Timelock delay/role changes themselves follow OZ governance; the deployment must preserve its intended delay and proposer policy.

This change requires a new Vault deployment and constructor updates in deployment clients. It provides no migration of an existing Vault's balances, accepted roots or used nonces. The signing node must read the current signer epoch and reconcile against the deployed Vault before releasing authorizations.

## Staking and the operator election

`Staking.sol` holds staked MONKEY, enforces the unstake cooldown, and emits `Staked`, `UnstakeStarted` and `UnstakeCompleted`. New stake is undelegated, and undelegated stake abstains. A staker delegates chosen amounts of its undelegated stake to any number of candidates with `delegate(candidate, amount)`, moves an amount from one candidate to another in one call with `redelegate(from, to, amount)`, and takes an amount back with `undelegate(candidate, amount)`, which emit `Delegated`, `Redelegated` and `Undelegated` with the amount. `delegatedTo(staker, candidate)` is one delegation, `delegatedStake(staker)` the part of the stake its delegations hold, and `delegationsOf(staker)` every delegation in one call. `votes(candidate)` is the sum of the amounts delegated to it, and `totalStaked()` excludes unstaking amounts. `startUnstake` takes undelegated stake first, then reduces each delegation in proportion: from the last in `delegationsOf` order to the first, each gives the amount still to take times its share of the delegations not yet reduced, rounded down, so the first gives exactly what remains and the votes stay exact. It emits `Undelegated` for each reduction before `UnstakeStarted`, so the events alone track every delegation. Votes drop at `startUnstake`, though the unstaking amount keeps earning distributions through the cooldown. A staker may hold any number of delegations. An unstake no larger than the undelegated stake reads none of them; a larger one costs about 16k gas for each delegation it reduces and 25k for each it empties (`test_GasOfAnUnstakePerDelegation` reports both), so a staker with many delegations takes some back first, each call touching one or two, to keep the unstake within the block gas limit. Delegation changes nothing about distributions.

`OperatorRegistry.sol` elects the operator whose key signs the engine's admin commands. Its constructor deploys `Staking`, which records the registry as the only caller of `lockBond` and `releaseBond`; deploy `Staking` only this way. The constructor takes the MONKEY token, the staking cooldown and distribution epoch, the timelock, the initial operator in effect (its admin key, 48-byte launch measurement, and config hash), and the election parameters with the lowest and highest value of each. The parameters are the epoch length, the minimum term, the finality margin, the challenger's margin in basis points of the incumbent's votes, the eligibility share and quorum in basis points of total stake, the candidate cap (at most `CANDIDATE_LIMIT`, 100, which bounds a close's gas), and the minimum self-bond. Their production values and bounds are not set here.

- `register` records the caller's admin key, self-bond, API hostname, handover endpoint and release, `keccak256(launchDigest ‖ configHash)` as the vault names a release, and locks the self-bond in `Staking`; it carries the admin key's EIP-712 authorization of the candidate (`registrationDigest`, the same typed-data vocabulary as the vault's withdrawals), so a key is registered only for a candidate it authorized. `startUnstake` cannot take it while the candidate is registered nor for one cooldown after `deregister`. Admin keys are unique among candidates. The operator in effect, and a candidate elected and waiting to take effect, cannot deregister.
- The timelock's `setReleaseApproval` approves a candidate's own release. Approval lists the candidate in `candidateList` under the candidate cap — only approved candidates count toward the cap and enter the list, so unapproved registrations cannot fill it; withdrawing approval delists the candidate while it stays registered, and a re-registration whose release is still approved relists at once.
- A candidate moves its candidacy to another release the timelock approved for it with `setRelease`, reverting `ReleaseNotApproved` otherwise. A move is one-way: it withdraws the approval of each release it leaves — the candidacy's, and for the operator in effect the one it ran, which the deployment or an installation may have named apart from its candidacy — reporting each approval withdrawn (`ReleaseApprovalChanged(candidate, left, false)`), so moving back needs a new approval. A delisted candidate's move relists it under the cap, so keeping a candidate off the list means withdrawing every release approved for it; the operator in effect may take one place beyond the cap, so a full list never blocks its upgrade, unless an operator an installation replaced took that place first: the list stays at most one over the cap, and the timelock frees a place by withdrawing an approval or raising the cap. When the caller is the operator in effect, its operator release moves too, so while rotation is on the vault names the new release at once and `syncRelease` raises the generation: this is how the operator in effect upgrades while `setCurrentRelease` is closed to the timelock. An installed operator moves the same way once it is registered, with the approvals the timelock granted its candidacy; an installation changes no candidacy, so the operator it replaces keeps its release, approvals and listing, and its moves no longer reach the vault. While an election or promotion waits to take effect, the operator it replaces and the candidate it names cannot move (`ElectionPending`), so the pending release and the handover source stay as the election made them. `CandidateReleaseChanged` reports each move.
- A candidate is eligible while it is listed, its self-bond meets the minimum, and its votes meet the eligibility share.
- Anyone calls `closeEpoch` once the open epoch has ended; unclosed epochs are skipped. While rotation is on and no election waits to take effect, the close elects the eligible candidate with the most votes, the earlier registration on a tie, when it is not the operator in effect, listed candidates' votes reach the quorum, the operator in effect has served its minimum term since it took effect, and the winner's votes exceed the incumbent's by the margin (an incumbent that is not eligible has none). `Elected` names the epoch, candidate, admin key, release, and the effective time, seven days plus the finality margin after the close. `operatorInEffect()` returns the election from that time.
- Only the timelock calls `setRotation`, off at deployment with the initial operator in effect; turning it off cancels an election not yet in effect, which `RotationChanged(false, true)` reports. It also approves releases and calls `setParameters` within the deployment bounds. While rotation is off it alone may also call `installOperator(candidate, adminKey, launchDigest, configHash)`, the fallback for a failed operator whose key is gone, seating the named operator in effect at once, behind the timelock's delay; `OperatorInstalled` reports it, and the engine mirrors it from protocol V48. It reverts with `RotationActive` while rotation is on.
- While rotation is on and the vault has had no checkpoint for `parameters.livenessTimeout`, anyone may call `promote`, which reverts with `NoQualifiedStandby` when no eligible candidate other than the operator in effect exists, leaving the operator unchanged. The promotion is the pending election for the eligible candidate with the most votes (the earlier registration on a tie), effective seven days plus the finality margin out, emitting the same `Elected` event a close does, so the engine mirrors it as an election; the vault's current release is the pending-or-current operator's from that moment. The timelock calls `setVault` once after deployment so the liveness clock is the vault's own `lastCheckpointAt`. A candidate updates its registered enclave address with `setEnclave`, which the timelock-gated `setSigner` installs while rotation is on: the vault reads the pending-or-current operator's candidate's enclave, reverting `NotTheRegisteredEnclave` for any other address. A standby that takes over with fresh keys registers them this way before the timelock installs them.

The engine mirrors `RotationChanged` and `Elected` from protocol V37 on the staking pipeline, and `OperatorInstalled` from `V48`. `RegistryLens.sol` is a stateless, read-only view over a registry, deployed beside it at any time and outside custody: `overview()` returns the switch, the parameters, the open epoch, total stake and the named, in-effect and pending operators, and `candidates(start, limit)` pages the listed candidates with their registration, votes, eligibility and role (`Candidate`, `Elected` or `Operator`). One call for all 100 costs about 4M gas; the node reads it in pages of 25 for `GET /v1/operators`. `RegistryLens.t.sol` runs it at 100 candidates against the registry's own getters. `OperatorRegistry.t.sol` covers candidacy, approvals, the close's rule and its boundaries, the switch and cancellation, and the timelock-only installation; `ReleaseChange.t.sol` covers release moves, the operator's upgrade through the vault, and how moves and installations meet; `OperatorRegistryInvariant.t.sol` checks vote and stake accounting, locked self-bonds, that only elections made while rotation is on move the role, that releases move only to approved ones and never for either side of a waiting election, that listing follows the approval of the release a candidacy holds, and that an elected operator runs its candidacy's release.

## Checkpoints and approval proofs

`postCheckpoint` retains the #24 digest and ABI: `keccak256("engine.checkpoint.v2" || uint64(chainId) || vault || uint64(seq) || root || bool(hasParent) || uint64(parentSeq) || parentRoot)`, using packed, big-endian integers. A checkpoint must increase sequence and name the exact latest accepted parent. Only one competing child can commit; stale-parent signatures cannot be relabeled with another parent.

`checkpointRoots(seq)` and `hasCheckpointAt(seq)` retain every accepted root. Claims can use older roots, which protects approvals still unpaid after later checkpoints remove or change their leaves. Roots rejected by the parent fence never become claimable. Storage grows by a bounded number of words per posted checkpoint; history has no eviction because there is no on-chain authority for deciding that every approval in a root is paid.

`checkpointSignerAt(seq)` and `checkpointEpochAt(seq)` record the signer and epoch when that exact checkpoint was accepted, and remain unchanged by later rotations. `totalWithdrawn()` counts cumulative USDC base units successfully paid; it changes atomically with the nonce, transfer and payment event, and never increases on a reverted claim. Checkpoint RPC reconciliation reads these fields at one canonical finalized block with the token balance and nonce-use status.

An approval key is `keccak256(abi.encodePacked(uint8(32), address account, uint64 nonce))`. Its value hash is `keccak256(abi.encode(address account, uint256 amountUsdc, uint64 nonce, uint64 approvedSeq))`. The compressed sparse Merkle tree hashes leaves as `keccak256(0x00 || key || valueHash)` and branches as `keccak256(0x01 || left || right)`. Siblings are supplied root-to-leaf, at most 256, and folded backwards with the key's bits from most significant to least significant. A single-leaf root takes an empty proof. Claims require an accepted checkpoint sequence at least as large as `approvedSeq`.

## Log heads

`LogHeads.sol` takes the enclave's newest released `(seq, link)` — where `link` is the cumulative
command-prefix digest, a running hash over every command's sealed bytes that checkpoints do not
reset, so a posted head commits to the whole history — under an `engine.log-head.v1` signature:
`keccak256("engine.log-head.v1" ‖ uint64(chainId) ‖ vault ‖ uint64(epoch) ‖ uint64(seq) ‖ link ‖
uint64(parentSeq) ‖ parentLink)`, packed. `post` is permissionless to relay; the recovered signer
must be the vault's current `checkpointSigner`, and the digest binds the vault's current
`signerEpoch`, so a rotation moves posts to a new epoch key. Every post names its parent — the
previously accepted head of the same epoch — and the contract requires an exact match against the
head it holds (`NotParent`) plus a strictly greater seq (`NotNewer`), so a longer divergent copy
cannot overwrite the anchor without extending it; the first post of an epoch carries no parent and
any seq. A node restarting from a log that does not reproduce the posted head refuses to start, so
a truncation older than the posting interval plus inclusion cannot resume unnoticed. The contract
has no admin: the vault reference is immutable, and a new vault deployment pairs with a new
LogHeads. `LogHeads.t.sol` covers the signature vector, newest-per-epoch, the parent fence, fuzzed
stale and replayed seqs, a forged signer and modified fields, another vault or chain, and rotation
into a new epoch.

## Withdrawal authorization

The domain is `EIP712Domain(string name,string version,uint256 chainId,address verifyingContract)`, with name `EngineWithdrawal`, version `1`, the current chain id and this Vault address. OZ `EIP712` builds the domain separator. The exact typed struct is:

```text
Withdrawal(address account,uint256 amount,uint64 nonce,uint64 approvedSeq,uint64 signerEpoch,uint64 issuedAt,uint64 expiresAt)
```

`withdraw(Withdrawal withdrawal, uint64 checkpointSeq, bytes32[] siblings, bytes signature)` is permissionless to relay and always transfers to `withdrawal.account`. `withdrawalDigest` exposes the EIP-712 digest. The signature must recover the current enclave signer using OZ ECDSA, and its epoch must equal the current epoch. `issuedAt` and `expiresAt` are Unix seconds; expiry is exactly 86400 seconds after issue, issue cannot be in the future, and expiry must be strictly after the claim's block timestamp.

An account/nonce pair can pay once across checkpoints, reissues and signer epochs. `usedNonces(account, nonce)` exposes payment status. Amounts are integer USDC base units without conversion or rounding; zero amounts, the zero account and the Vault as recipient are rejected. All entry points that transfer tokens are non-reentrant. A claim consumes its nonce before `SafeERC20` transfer, and checks both the vault debit and recipient credit equal the approved amount. A failed, fee-bearing or otherwise inexact outgoing transfer reverts atomically, preserving funds and the nonce. `WithdrawalPaid(account, amount, nonce, approvedSeq)` gives node reconciliation the full approval identity.

## MONKEY and USDC claims

`claimEmissions(address account, uint256 entitled, uint64 checkpointSeq, bytes32[] siblings)` and `claimDistribution(address account, uint256 entitled, uint64 checkpointSeq, bytes32[] siblings)` are permissionless to relay and always pay `account`. Each proves the account's cumulative amount (key `keccak256(abi.encodePacked(uint8(8), account))` for an entitlement and `uint8(13)` for a distribution, value `keccak256(abi.encode(entitled))`) against `checkpointRoots(checkpointSeq)`, and pays what it adds to `emissionsClaimed(account)` or `distributionsClaimed(account)`, reverting with `NothingToClaim` when it adds nothing. So a proof stays good while later checkpoints post, and a trader's wallet can take its time.

The checkpoint must be recorded (`UnknownCheckpoint`) in the signer epoch in force (`InvalidSignerEpoch`), and the signer must not be retired (`NoSigner`): a rotation or a guardian's retirement ends the claims on every earlier root, for good. The next signer's first checkpoint proves at least as much, and the vault pays it less what was already paid, so nothing is lost while one can still post. Once the exit has started none can: USDC is then registered against the exit root, and MONKEY not yet minted when its signer was replaced or retired stays unminted.

An older root cannot overpay, because each amount only grows: the engine adds to an entitlement when an emission period closes and to a distribution when a staking epoch closes, and nothing reduces either, a reversed deposit included, which becomes an emission debt against later weight. `entitled` at an older root is therefore at most what the newest root holds, the vault pays no more than was due at that root, and a later root pays the rest. Each USDC payment counts in `distributionsPaid`, which node reconciliation adds to the vault's balance and compares with what the engine allocated by the checkpoint the vault last recorded, so it holds whichever root a claim names.

## Exit against the last posted root

`lastCheckpointAt()` is the block time of the latest accepted checkpoint, or of deployment before the first. Once `checkpointsStale()`, `staleAfter` seconds after it, every deposit route and `bookSurplus` revert with `CheckpointsStale` until a checkpoint is posted. Once `exitPeriod` seconds have passed, anyone may call `startExit(terms, siblings)`, which proves the root's exit terms leaf (key `keccak256(abi.encodePacked(uint8(24)))`, value `keccak256(abi.encode(uint64 depositCursor, int128 pending, int128 held, int128 unheld, uint64[] gaps))`) against `latestRoot`, or, with no checkpoint ever posted, takes a cursor of zero. Every deposit id at or past the cursor is refunded; `gaps` lists the lowest 64 ids below it the root does not hold, which only a reorganisation the engine was still applying leaves, and the vault refunds them too, marking them in `exitRefundableGap`. `unheld` commits the principal of every id below the cursor the root does not hold, the named gaps included: the reserve holds it, and whatever no gap names stays in the vault rather than reaching the pools. The exit is permanent: `postCheckpoint`, `withdraw` and `claimDistribution` revert with `ExitActive`, and deposits stay refused. Neither pause nor the signer epoch applies to anything below. `claimEmissions` stays open under its own rule, on any recorded root of the signer epoch in force while the signer is not retired, and pays no USDC.

The vault records each deposit's payer and amount (`depositRecords(id)`), and `refundableThrough(id)` the running total of payer-funded deposits, booked surpluses aside. At the start, the exit reserves every payer-funded deposit from the cursor on that the root does not hold, and the root's pending principal rounded up, in `exitRefundReserve`, and the held principal rounded up in `exitHeldReserve`, which it never pays. A cursor past the vault's deposit count is taken as that count. `refundDeposit(id)` pays a deposit from the cursor on that the root does not hold back to its payer, and `refundPendingDeposit(chainRef, pending, siblings)` one the root holds pending (key `keccak256(abi.encodePacked(uint8(34), chainRef))`, value `keccak256(abi.encode(uint64 depositId, address account, address payer, int128 amount))`) whose vault record has the same payer and amount; each deposit is refunded once, at any time after the start, from the reserve.

For `claimWindow` seconds after the start, anyone may register for an account, each once: `registerExit` its equity at the root's marks, through `ExitVerifier.accountClaim`, which proves the account leaf, exactly its `openPositions` position leaves in strictly increasing markets, and each one's market leaf, values each position's `(mark - entry) * qty` rounded down and converted to USD at the market's FX mark rounded down, and floors the sum with the balance at zero, in whole base units rounded down; `registerExitWithdrawal` an approval leaf whose nonce is unused, which it then marks used; `registerExitQueued` a queued request's remainder (value `keccak256(abi.encode(address account, int128 amount, int128 remaining, uint64 requestedSeq, uint64 ticket))`); and `registerExitDistribution` the part of a distribution leaf not already claimed. After the window, the first `claimExit` or `releaseHouseRemainder` fixes the pools: what the vault holds beyond both reserves goes to client claims, up to their total, then to distribution claims, up to theirs, and the rest is `houseRemainder`. `claimExit(account)` pays an account its claims times each pool over that pool's total, rounded down, once; `releaseHouseRemainder(to)`, callable only through the timelock, pays the remainder once.

`ExitVerifier`, which the vault deploys, holds no state; the vault compiles within EIP-170's size limit only with the optimizer, which `foundry.toml` enables. `StateTree` is the shared proof check.

## Daily turn seeds

`SeedSchedule.sol` fixes which beacon epoch's RANDAO mix seeds each daily operator turn: turn `n` starts at 22:30 UTC on day `n` of the Unix epoch, its draw deadline is a day earlier, and its seed is the mix at the end of the epoch holding the time two days before the deadline, counted from the beacon genesis time each contract is deployed with (`seedEpoch`, `drawDeadline`). Consecutive turns' epochs are 225 apart.

`SeedRelay.sol` on Ethereum proves a turn's mix and sends it to the receiver as an Arbitrum retryable ticket that `msg.value` pays. `relay(turn, witness, fees)` takes an execution block's time, whose EIP-4788 entry is the witness header's root; the header; the state's `fork.current_version` with its 8-sibling branch; and the seed with its 22-sibling branch to `randao_mixes[epoch % 65536]`. It refuses a turn past its draw deadline, a root EIP-4788 no longer holds (it keeps about 27 hours), a header that does not hash to it, a state not past the epoch or past the slot at which the mix's index is reused, a fork version it was not deployed with, and a branch that does not verify. Each branch is checked with the consensus specification's `is_valid_merkle_branch` over the SHA-256 precompile. The ticket refunds unspent fees to the caller on Arbitrum, and its beneficiary is the receiver, which cannot cancel it, so a ticket whose redemption fails stays redeemable by anyone. Anyone may relay, and a turn may be relayed again; only the first delivery counts.

`SeedReceiver.sol` on Arbitrum records a seed only from the relay's address with Arbitrum's L1-to-L2 alias applied, only for the epoch the schedule fixes for its turn, and only before the turn's draw deadline. `seedOf(turn)` answers from the deadline on: the relayed seed, or `keccak256(abi.encode(s, turn))`, where `s` is the seed of the latest earlier turn that has one; it refuses before any turn has a seed. Neither contract has an admin.

Deploy the receiver on Arbitrum naming the relay's address before the relay exists, from the deployer's next nonce on Ethereum, then the relay with the receiver's address, both with the network's beacon genesis time (`1606824023` on mainnet); check that the relay landed at the address the receiver names. The relay takes the fork versions whose states it reads, each one whose `BeaconState` keeps the Electra-onward 64-field layout: on mainnet, `0x05000000` (Electra) and `0x06000000` (Fulu). A fork that changes the layout needs a new pair. The registry names the receiver in the launch deployment.
