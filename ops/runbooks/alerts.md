find the alert's name here and follow the runbook that its row names. Commands, configuration keys
and output call a running trading server a node.

## How alerts work

An alert is a line in the trading server's log that carries `alert = "<name>"`. A line at level
`error` is a **Critical** alert, and a line at level `warn` is a **Warning**. A later line that
carries `alert_resolved = "<name>"`, with the same fields, ends the alert.

When `[alerts.critical]` and `[alerts.warning]` are configured, the trading server posts the start
and the end of each episode as JSON to the webhook whose URL each section's `url_secret` names. A
page carries these fields:

- `status`, which is `firing` or `resolved`;
- `severity` and `alert`;
- `key`, which is the same for the start and the end of an episode, so that a receiver can match
  them;
- `summary`, the log line's `fields`, and its `context`.

Each page is delivered at least once. A repeat with the same key does not page again until the alert
has been quiet for `alerts.episode_quiet`. Each page is stored in the alert outbox before it is
first posted, so it survives a restart.

Without a webhook, the alerts of that severity are only logged. A trading server whose enclave or
custody is not the mock refuses to start without `[alerts.critical]`.

Critical alerts are the ones to wake someone for. The code decides which alerts are Critical, and
the owner's rota in [Contacts](incident-response.md#contacts) decides who is woken.

## Start-up refusals

Most of these alerts appear as `refusing to serve: <cause>`, after which the image powers off the
virtual machine. Six of them do not stop the trading server by themselves: `secret_missing`,
`secrets_unreadable`, `secret_unusable`, `signer_unregistered`, `legacy_deposit_unproven` and
`log_tail_lost`.

| Alert | Level | What it means and what to do |
| --- | --- | --- |
| `secret_missing` | Critical | This alert does not by itself stop the trading server. No delivered bundle holds a secret that the configuration names. Without a chain key or a screening key, the trading server holds, and serves only its delivery listener. Without a vendor key, that vendor's connection stays off. Without a webhook URL, that alert route stays off. Follow [Secrets](key-recovery.md#secrets). |
| `secrets_unreadable` | Critical | This alert does not by itself stop the trading server. This release's sealed secrets file does not open, so the trading server runs as if it held no secrets until a delivery replaces the file. Follow [A sealed secrets file is lost or does not open](key-recovery.md#a-sealed-secrets-file-is-lost-or-does-not-open). |
| `secret_unusable` | Critical | This alert does not by itself stop the trading server. A sealed webhook URL is not acceptable, so its alert route stays off. Deliver an acceptable URL, as [Deliver secrets](key-recovery.md#deliver-secrets) describes. |
| `secrets_start_failed` | Critical | The trading server's first read of the chain failed with a delivered key. Its delivery listener stays up for five minutes, or until a new bundle is sealed and its receipt has gone out, and then the image powers off the virtual machine. If the provider refused the key, deliver a working key and start the virtual machine again. If the trading server has no sealed keys yet, give it the `new-key` or `predecessor` file that its first start had. Otherwise, follow [Checkpoint endpoint](feed-and-custody-failures.md#checkpoint-endpoint). |
| `clocksource_unprotected` | Critical | The guest kernel keeps time on a clock other than the TSC that Secure TSC protects, and the host can scale that clock. Alternatively, the hardware reports the guest TSC's frequency below 1000 MHz, in which case the kernel calibrates against clocks that the host emulates. Follow [The trading server will not start](restart-and-recovery.md#the-trading-server-will-not-start). |
| `enclave_key_failed` | Critical | The sealed keys cannot be opened or created. Follow [How the enclave key is kept](key-recovery.md#how-the-enclave-key-is-kept). |
| `sealed_certificates_unreadable` | Critical | This release's sealed certificate file does not open, because the host altered it or gave the trading server another release's file. The trading server refuses to start before it opens or takes the keys. Follow [The sealed certificate does not open](certificate-renewal-failure.md#the-sealed-certificate-does-not-open). |
| `signer_unregistered` | Critical | This alert does not stop the trading server. The vault does not name this key, so the trading server serves only `/v1/attestation`. Follow step 5 of [First deployment](deploy-and-rollback.md#first-deployment). |
| `custody_connect_failed` | Critical | The custody adapter could not start, because the providers are unreachable or disagree. Follow [Custody RPC providers](feed-and-custody-failures.md#custody-rpc-providers). |
| `checkpoint_startup_failed` | Critical | The trading server refused to start for one of three causes. The log fails the checks against the vault, before anything is written. The checkpoint endpoint cannot be read. Or, when the log or the configuration's genesis holds a staking configuration, the staking contract cannot be read through the custody providers. Follow [The trading server will not start](restart-and-recovery.md#the-trading-server-will-not-start). |
| `log_rollback` | Critical | The log head posted on chain names sequence numbers, or a cumulative command-prefix digest, that this log does not hold. At start, the trading server refuses before it writes anything. While it runs, a posted head that overtakes it, or that names another prefix at a sequence number it retains, freezes sequencing. The cause is a truncated log, or a second copy running on this key. A start from a recovery cache also raises it when the log's instructions between the posted head and the cache are damaged. Follow [A log the posted head does not hold](restart-and-recovery.md#a-log-the-posted-head-does-not-hold). |
| `log_recovery_failed` | Critical | The log fails recovery. The usual causes are a configuration that differs from what the log records, a bad signature or root, and an unsealed instruction. Follow [The trading server will not start](restart-and-recovery.md#the-trading-server-will-not-start). |
| `history_recovery_failed` | Critical | The account history index cannot be opened or repaired. Follow [Rebuild the derived stores](restart-and-recovery.md#rebuild-the-derived-stores). |
| `marks_cache_failed` | Critical | The marks cache cannot be opened or activated. Follow [Rebuild the derived stores](restart-and-recovery.md#rebuild-the-derived-stores). |
| `staking_terms_mismatch` | Critical | The staking epoch or cooldown that the log, or the configuration's genesis, records differs from the staking contract's. Follow [The trading server will not start](restart-and-recovery.md#the-trading-server-will-not-start). |
| `emission_budget_mismatch` | Critical | The log's emission schedule differs from the cap on MONKEY that the vault holds. Follow [The trading server will not start](restart-and-recovery.md#the-trading-server-will-not-start). |
| `genesis_refused` | Critical | The configuration's genesis does not apply to this log. Follow [The trading server will not start](restart-and-recovery.md#the-trading-server-will-not-start). |
| `protocol_activation_failed` | Critical | The newest protocol version does not activate on this log. Follow [The trading server will not start](restart-and-recovery.md#the-trading-server-will-not-start). |
| `benchmark_sync_prerequisites_missing` | Critical | A log with a rollover schedule has not recorded its client authentication, its operator or its toxicity weighting. Follow [The trading server will not start](restart-and-recovery.md#the-trading-server-will-not-start). |
| `collateral_relay_failed` | Critical | The relay of the vendor's attestation collateral could not be set up. The usual cause is a missing `tee.processor`. Follow [The trading server will not start](restart-and-recovery.md#the-trading-server-will-not-start). |
| `log_heads_startup_failed` | Critical | With `[log_heads]` configured, the posted head could not be read through the custody quorum within the finality budget, or the head poster's setup failed. The trading server refuses to serve, because it cannot bound how far its log could be cut back. Follow [The trading server will not start](restart-and-recovery.md#the-trading-server-will-not-start) and [Custody RPC providers](feed-and-custody-failures.md#custody-rpc-providers). If the message names a mismatch in the log-head submission's deployment, `log_heads.relayer` or `log_heads.contract` has changed. The stored reservation then carries no authority, so move `/data/log/log-head-submission.json` aside and start again. |
| `legacy_withdrawal_unproven` | Critical | A withdrawal inherited from an older log has no canonical finality proof. Follow [The trading server will not start](restart-and-recovery.md#the-trading-server-will-not-start). |
| `legacy_deposit_unproven` | Critical | This alert does not by itself stop the trading server. Legacy principal stays locked, because no exact canonical receipt was established for it. The alert fires only on a log that inherited credits from before deposit finality, and it is not expected in production. Call the owner. |
| `log_tail_lost` | Critical | This alert does not by itself stop the trading server. Recovery found that the log ends before instructions that signed heads cover, so instructions that clients saw acknowledged are missing from this disk. Follow [The books look wrong](incident-response.md#the-books-look-wrong). |

## Running faults

These alerts mean that part of the trading server has stopped or stalled.

| Alert | Level | What it means and what to do |
| --- | --- | --- |
| `secrets_restart_required` | Warning | A bundle is sealed that the running trading server does not use, because a running trading server keeps the secrets it started with. Restart it when the rotation is ready, and revoke the old key afterwards. Follow [Rotate a secret](key-recovery.md#rotate-a-secret). |
| `sequencer_failed` | Critical | The sequencer's thread stopped with an error, and the trading server exits. Follow [After any restart](restart-and-recovery.md#after-any-restart). |
| `task_stopped` | Critical | A supervised task stopped, so the trading server stops. Follow [After any restart](restart-and-recovery.md#after-any-restart). |
| `log_sync_held` | Critical | The oldest batch not yet synced has waited more than 5 s for its log sync. Until the sync finishes, the sequencer takes no request, so nothing is stamped behind the batch. An honest disk syncs in milliseconds, so the cause is a stalled or full disk, or a host that is holding the sync. The alert resolves when the sync finishes. Its page is first committed to the alert outbox on the same disk, so a hold of the whole disk delays the page. The gauge `engine_log_sync_held`, which the Prometheus rule `EngineLogSyncHeld` reads, reports the hold from memory. Four syncs run outside this bound and page only as `sequencer_stalled`: the snapshot capture's sync, the checkpoint's catalog maintenance, a rotation's catalog fold, and a handover's segment seal. A hold that lasts `alerts.no_price_after` beyond the bound also raises `sequencer_stalled`, from the same cause. Check the host's disk, then follow [Restart a healthy trading server](restart-and-recovery.md#restart-a-healthy-trading-server). |
| `sequencer_stalled` | Critical | The sequencer has answered no monitoring sample for `alerts.no_price_after`. If `log_sync_held` is open, a held log sync is the cause. Follow [Restart a healthy trading server](restart-and-recovery.md#restart-a-healthy-trading-server). |
| `history_drain_timed_out` | Warning | At shutdown, the history did not finish reading the stream in time, and it was stopped. The alert fires only at shutdown. Nothing needs to be done unless it repeats at every stop. |
| `checkpoint_accounting_overflow` | Critical | Checkpoint accounting refused the engine's output, and the sequencer refuses further instructions. Follow [The books look wrong](incident-response.md#the-books-look-wrong). |
| `response_signing_failed` | Critical | A response body could not be read for signing, so an internal error reached a client. Read the console lines around the alert. If it repeats, keep the evidence, as [Keep the evidence](incident-response.md#keep-the-evidence) describes, and restart the trading server. |
| `archive_unreadable` | Critical | The archive route could not read a checked segment, so an internal error reached a client. Read the console lines around the alert. If it repeats, keep the evidence, as [Keep the evidence](incident-response.md#keep-the-evidence) describes, and restart the trading server. |
| `history_unreadable` | Critical | The history route could not read the index. Follow [Rebuild the derived stores](restart-and-recovery.md#rebuild-the-derived-stores). |
| `marks_unreadable` | Critical | The marks route could not read the cache. Follow [Rebuild the derived stores](restart-and-recovery.md#rebuild-the-derived-stores). |
| `stream_backfill_failed` | Critical | A stream subscriber's catch-up from disk failed, and that subscriber's stream ended. If it repeats, keep the evidence, as [Keep the evidence](incident-response.md#keep-the-evidence) describes, and restart the trading server. |
| `stream_encode_failed` | Critical | A stream message could not be encoded, and that subscriber's stream ended. If it repeats, keep the evidence, as [Keep the evidence](incident-response.md#keep-the-evidence) describes, and restart the trading server. |

## Derived stores and optional caches

The trading server rebuilds these stores from the log. None of these alerts affects the books.

| Alert | Level | What it means and what to do |
| --- | --- | --- |
| `history_index_discarded` | Warning | The history index is being rebuilt from the log. Follow [Rebuild the derived stores](restart-and-recovery.md#rebuild-the-derived-stores). |
| `history_index_damaged` | Warning | The history index is damaged, and history pages are withheld until a verified repair. Follow [Rebuild the derived stores](restart-and-recovery.md#rebuild-the-derived-stores). |
| `history_head_rejected` | Warning | A pointer file in the history directory was ignored, and it is rebuilt. Nothing needs to be done. |
| `history_head_write_failed` | Warning | The pointer to the latest complete history could not be written. The pointer is optional. Check the data disk's space and health. |
| `history_rows_replayed` | Warning | The history index reached a rollover whose financing rows were neither in memory nor stored. It therefore replays the log from its start, on an engine of its own beside the sequencer's, to derive the rows. History pages wait until the replay passes that rollover. The alert is expected after the index was rebuilt, and when a member's first index starts from a log whose rollovers the member never followed. If it repeats on an operator that has not restarted, check that the history keeps up. |
| `financing_rows_rejected` | Warning | The financing read could not prove a rollover's rows from the history's `financing` directory, so it answers 404 for that rollover. A client can still prove the rows by replaying the log. The alert's error names one of two causes. If the stored rows do not give the root that the log holds, the host changed or damaged the file, and the history writes it again only when it takes that rollover again, as after a rebuild. Check the data disk's health and who can write to it, then rebuild the history index, as [Rebuild the derived stores](restart-and-recovery.md#rebuild-the-derived-stores) describes. A rebuild through the log's replay writes every retained rollover's file again. With `[snapshots]`, a history that resumes from its snapshot store replays nothing, so a rollover before the snapshot has no file until it leaves the retention, and its read answers 404 with no alert. If the log could not be read at that sequence number, as for an unreadable segment or a catalog proof that fails, the fault is in the log and not in the rows file, so follow the log's own alerts. |
| `financing_rows_unstored` | Warning | A rollover's financing rows could not be written to the history's `financing` directory. Once the rows leave memory, a week of rollovers later, the financing read cannot prove them. Check the data disk's space and health. |
| `daily_snapshot_failed` | Warning | A daily snapshot was not published at the first checkpoint of a UTC day, or the writer did not start. The alert fires only with `[daily_snapshots]`. The log stays the authority: an audit that replays in ranges merges that day's range with the next, and the node tries again at the next day's first checkpoint; a day on which the writer was still busy with the last one has none. A writer that did not start publishes nothing until the node restarts. Follow [Daily snapshots](restart-and-recovery.md#daily-snapshots). |
| `daily_snapshot_unreadable` | Warning | A request for a daily snapshot failed: the snapshot directory's manifest or the file could not be read, or the file differs from its listing, and the request answered 500. Fires only with `[daily_snapshots]`. The log and its archive are untouched, and an audit takes the day's range from the snapshot before. A damaged file stays listed: stop the node, remove the file and its line in the directory's `manifest.jsonl`, and start it again. Follow [Daily snapshots](restart-and-recovery.md#daily-snapshots). |
| `snapshot_rejected` | Warning | A recovery snapshot was ignored. The alert fires only with `[snapshots]`. Recovery falls back to an earlier snapshot, or to a full replay, which takes longer as the log grows. Nothing needs to be done. |
| `snapshot_write_failed` | Warning | A recovery snapshot could not be written, and the checkpoint stays in the log. The alert fires only with `[snapshots]`. A restart then replays from an older snapshot, or the whole log. Check the data disk's space. If `stats_scan_inline` fired too, the stats worker that encodes snapshots stopped, and the trading server encodes them itself, holding instructions for a second or two each time. |
| `snapshot_cleanup_failed` | Warning | The cleanup of old caches or snapshot publications was deferred, and old caches stay until the next write. Check the data disk's space. |
| `log_catalog_unavailable` | Warning | The archive catalog's maintenance was deferred. Completed segments wait in memory, and then the active segment grows. The trading server keeps sequencing. The usual cause is the data disk, so check its space and health. |
| `log_rotation_failed` | Warning | A new log segment cannot be started, so the current segment grows. The trading server keeps sequencing. The usual cause is the data disk, so check its space and health. |
| `marks_cache_discarded` | Warning | The marks cache failed validation, and it is being rebuilt. Follow [Rebuild the derived stores](restart-and-recovery.md#rebuild-the-derived-stores). |
| `marks_cache_rebuilt` | Warning | The marks cache is being rebuilt after a refused reset or a failed validation. Follow [Rebuild the derived stores](restart-and-recovery.md#rebuild-the-derived-stores). |
| `marks_prior_cache_dropped` | Warning | A prior marks cache could not be read, or has another schema, and was not imported. It is rebuilt from the log. Nothing needs to be done. |
| `marks_prior_rows_dropped` | Warning | Prior marks rows failed authentication and were not imported. Those rows are rebuilt from the log. Nothing needs to be done. |
| `marks_samples_dropped` | Warning | The marks queue was full, and samples were dropped. The dropped samples are seeded again at the next recovery. If the alert repeats, look at the sequencer's load in `engine_sequencer_queue_depth`. |
| `marks_seed_failed` | Warning | Seeding the marks cache from the log failed, and the cache is reset so that it is derived again. Follow [Rebuild the derived stores](restart-and-recovery.md#rebuild-the-derived-stores). |
| `stats_scan_inline` | Warning | The dashboard's background scan worker stopped, so its account scans, and with `[snapshots]` each recovery snapshot's encoding, run on the sequencer's thread and add to what each price waits behind. The books are unaffected. On a member between its turns, the scans run on the thread that follows the operator instead, and its next turn's start copies the state again before its first command, which at launch scale takes over a second. A restart starts the worker again, as [Restart a healthy trading server](restart-and-recovery.md#restart-a-healthy-trading-server) describes. |
| `marks_backfill_failed` | Warning | The optional backfill of candles from a provider failed, and it retries. History older than the log may be missing meanwhile. |

## Prices, markets and books

| Alert | Level | What it means and what to do |
| --- | --- | --- |
| `market_no_price` | Critical | An open market that a feed prices has no usable price. The time is counted from trusted time's first sample of the run, before which nothing is sequenced. A late first sample raises `trusted_time_no_sample` when a round takes no sample, and `trusted_time_unavailable` once the grace period has passed, but not this alert. Follow [A market has no price (`market_no_price`)](feed-and-custody-failures.md#a-market-has-no-price-market_no_price). |
| `market_unfed` | Warning | No configured feed prices this market, so it cannot be traded. Follow [Find what is down](feed-and-custody-failures.md#find-what-is-down). |
| `venue_feed_down` | Warning | A connection to a venue or a data vendor is down and retrying. For CME Group, the alert also fires when the connection has no bearer token to connect with. Follow [A crypto venue is down or quiet](feed-and-custody-failures.md#a-crypto-venue-is-down-or-quiet), [CME Group's feed](feed-and-custody-failures.md#cme-groups-feed) or [Alpaca's feed](feed-and-custody-failures.md#alpacas-feed). |
| `venue_symbol_silent` | Warning | A symbol has had no fresh quote while its market is open. Follow [A crypto venue is down or quiet](feed-and-custody-failures.md#a-crypto-venue-is-down-or-quiet). |
| `venue_stale` | Warning | For 2 s, or for `feeds.venues.timeout` if that is shorter, a venue has kept sending a symbol's order books that were already too old to count when it sent them. The message gives their age. The trading server resubscribes to the symbol until it is current. The alert's fields are `venue`, `feed`, `symbol` and `market`. Follow [A crypto venue is down or quiet](feed-and-custody-failures.md#a-crypto-venue-is-down-or-quiet). |
| `venue_market_unlisted` | Warning | A connection's configuration names a symbol for a market that the engine does not list, so that symbol's quotes are held back. The trading server raises the alert once for each such symbol, with the fields `venue`, `feed`, `symbol` and `market`, and resolves it when the engine's listings include the market. The cause is a venue entry in the configuration whose market is not in the launch listings. Compare the entry with the markets that [`GET /v1/markets`](../../docs/api.md) lists. Correcting a configuration is a new release, which [Deploy and rollback](deploy-and-rollback.md) describes. |
| `venue_contract_unlisted` | Warning | A connection's symbol names a futures contract that the market's listing does not name, names a contract for a market that is not priced from futures, or names none for a market that is, so that symbol's quotes are held back. The fields and the resolution are those of `venue_market_unlisted`. Compare the symbol's contract with the market's contracts in `GET /v1/markets`, and follow [Futures markets](feed-and-custody-failures.md#futures-markets). |
| `venue_token_failed` | Warning | CME Group's token endpoint failed or refused a request for a bearer token. The alert resolves at the next request that the endpoint grants. The alert's fields are `venue` and `feed`. Follow [CME Group's feed](feed-and-custody-failures.md#cme-groups-feed). |
| `venue_message_refused` | Warning | A venue's message was refused, or CME Group or Alpaca refused a login or a subscription. The message is quoted only from a venue that holds no credential. Follow [Find what is down](feed-and-custody-failures.md#find-what-is-down), [CME Group's feed](feed-and-custody-failures.md#cme-groups-feed) or [Alpaca's feed](feed-and-custody-failures.md#alpacas-feed). |
| `venue_clock_ahead` | Warning | A venue's timestamps are well ahead of the host's clock. Follow [Find what is down](feed-and-custody-failures.md#find-what-is-down). |
| `venue_delayed` | Warning | A venue's stream may be further behind than `feeds.venues.max_delay`, so its quotes do not count. Follow [Find what is down](feed-and-custody-failures.md#find-what-is-down). |
| `prices_rejected` | Warning | The engine refused a price update, for the reason in the message. Follow [Find what is down](feed-and-custody-failures.md#find-what-is-down). |
| `futures_roll_overdue` | Warning | A futures market is past its roll time, and no price gap between its contracts has been recorded. Follow [Futures markets](feed-and-custody-failures.md#futures-markets). |
| `futures_last_contract` | Warning | A futures market is priced from the last contract that its listing names. Follow [Futures markets](feed-and-custody-failures.md#futures-markets). |
| `benchmark_rate_missing` | Critical | A benchmark has no rate, so its markets accrue no financing. Follow [Benchmark rates](feed-and-custody-failures.md#benchmark-rates). |
| `benchmark_rate_stale` | Critical | The newest rate is more than five weekdays old, and it still applies. Follow [Benchmark rates](feed-and-custody-failures.md#benchmark-rates). |
| `benchmark_rate_undated` | Critical | A legacy rate with no date still applies. Follow [Benchmark rates](feed-and-custody-failures.md#benchmark-rates). |
| `benchmark_fetch_failed` | Warning | A fetch from a publisher failed. The history is kept, and the worker retries. Follow [Benchmark rates](feed-and-custody-failures.md#benchmark-rates). |
| `benchmark_sync_failed` | Warning | The benchmark worker's submission failed, and the worker retries. Follow [Benchmark rates](feed-and-custody-failures.md#benchmark-rates). |
| `benchmark_schedule_watch_failed` | Warning | The benchmark worker's watch of the rollover schedule dropped, and the worker reconnects. Follow [Benchmark rates](feed-and-custody-failures.md#benchmark-rates). |
| `benchmark_rate_refused` | Warning | The worker left out a published rate that the engine would refuse, because it moves more than 300 bps a day from the applied rates next to its date. The last applied rate keeps financing positions. Follow [Benchmark rates](feed-and-custody-failures.md#benchmark-rates). |
| `benchmark_sync_pending` | Warning | The trading server is waiting for the worker's signed history before it catches up. Follow [Benchmark rates](feed-and-custody-failures.md#benchmark-rates). |
| `benchmark_sync_skipped` | Warning | The registry installed an operator whose key has yet to take effect, so the trading server does not wait for the worker's history. Financing uses the last applied rates until a snapshot of rates applies, which resolves the alert. Follow [Benchmark rates](feed-and-custody-failures.md#benchmark-rates). |
| `corporate_action_failed` | Critical | A scheduled dividend or split failed, and no partial change was committed. Follow [When an action fails](corporate-actions.md#when-an-action-fails). |
| `house_deficit` | Warning | The house's net asset value is below zero. Trading continues within the floors of the exposure caps. Follow [When to make a market reduce-only](reduce-only.md#when-to-make-a-market-reduce-only). |
| `bad_debt` | Warning | An account's loss beyond its balance was written off against the house, which absorbed the loss. The alert is for information. Read it together with `house_deficit` and the house's net asset value, the `nav` field of `/v1/house`. |
| `house_loss_stress` | Warning | The house has lost money to its clients over the trailing day, counting open positions at current prices. Every priced market rises to the stress level that the message names, which widens the spread on every execution. The engine has already responded. The alert pages at most once a minute while the loss is above its threshold. It resolves once the house has stayed ahead on the day for a minute, and the markets step down after the cooldown. Read the loss in the `house_loss` field of `/v1/house/state`, and each market's positions by profit in `/v1/house/positions`. An honest day can fire this alert. If the same accounts keep winning despite the wider spreads, or if a market's price looks wrong, follow [When to make a market reduce-only](reduce-only.md#when-to-make-a-market-reduce-only) and [Incident response](incident-response.md). |

| `liveness_unconfirmed` | Critical | No other member confirmed the operator's log within one heartbeat interval of the first instruction past the newest confirmation, so instructions stop. With no newer head, the heartbeat stops and a promotion follows. Check the members' following, for `standby_follow_failed`, and their handover endpoints. The alert resolves when a member confirms. Follow [Minute-scale liveness](operator-candidate.md#minute-scale-liveness). |
| `liveness_fenced` | Critical | The operator's trading server signs no instruction, answer or head, because its upper bound on true time has reached its fence. The fence is 15 s before the earliest block time at which a promotion could pass. After a read showed that no promotion could pass, and with no read since, the fence is 15 s before the next turn boundary for a set with no other member, and 15 s after that boundary when no turn names the operator or there is no schedule. The trading server's reads of the chain failed or show no new head, because the chain's sequencer is down, the custody quorum is lost, or its heads are not landing, which `log_head_post_failed` shows. The alert resolves on a read that moves the fence on. If the vault names another key, the trading server stays stopped. Follow [Minute-scale liveness](operator-candidate.md#minute-scale-liveness). |
| `liveness_parameters_refused` | Critical | The schedule's heartbeat rule leaves `heartbeatMisses` × `heartbeatInterval` within the stop margin plus two round trips of a head, or `node.tick` is above half the interval. The trading server signs and sequences nothing. Fix `node.tick`, or have the timelock change the rule while no turn names the operator. |
| `liveness_member_conflict` | Critical | On the operator, a member's copy, or a head that the member saw, holds a different link from this log at some sequence number, and that member confirms nothing. On a member, its copy holds a different link from a signed head of the epoch, and it confirms nothing under that epoch. **Two histories exist under one key.** Stop, and compare the copies, as [Incident response](incident-response.md) describes. |
| `liveness_read_failed` | Warning | The operator's liveness rule could not read the chain. The fence runs on from the last read, and it stops the trading server if reads stay down. The alert resolves on a read. Follow [Custody RPC providers](feed-and-custody-failures.md#custody-rpc-providers). |
| `liveness_caller_read_failed` | Warning | A member's liveness caller could not read the chain, and it witnesses, promotes and relays nothing until it can. The alert resolves on a read. |
| `liveness_caller_unfunded` | Warning | `liveness.caller` holds less than `liveness.min_balance`, or a liveness call failed for lack of funds. Fund `liveness.caller`. The member's fallback fixer reads the balance for the trading server's whole life, whether the member follows or holds a turn, and the liveness caller reads it while the member follows, in one episode. The alert resolves once the balance is back above the minimum. Follow [Configure the liveness caller](operator-candidate.md#configure-the-liveness-caller). |
| `liveness_caller_fallback_failed` | Warning | A member's fallback fixer, which sends from `liveness.caller` for the trading server's whole life, cannot read the seed receiver, or cannot send a fix of a turn's fallback seed with `SeedReceiver.fixFallback`. The alert also fires while the fixer cannot read the caller's balance. While every member's fixer fails, a turn with no relayed seed, whose block nobody records within 256 blocks, is never drawn. Check the custody providers and the `[checkpoints]` endpoint, as for `liveness_caller_read_failed` and `liveness_caller_send_failed`. The alert resolves once a read, the balance read and any fix go through. Follow [When `seed_missing` fires](seed-relay.md#when-seed_missing-fires). |
| `liveness_caller_send_failed` | Warning | A member's liveness caller cannot estimate or send its witnesses, promotions and relays, or read its balance, for a reason other than a revert or a lack of funds. Its `[checkpoints]` endpoint is down or rotated, or does not sign for `liveness.caller`. Fix the endpoint. The alert resolves once a call goes through. |
| `standby_unregistered` | Warning | The schedule does not list this member's standby key as promotable. The trading server wrote the vouched registration to `standby-registration.json` in the sealing directory, and the alert names the call. Send that call from the candidate's account before the vouch expires. A promoted operator also raises the alert, for the replacement key it seals, because the promotion consumed the last one. A key that the schedule never took is kept across restarts, and sealing a new key removes the file. The alert resolves once the key is promotable. Follow [Register your standby key](operator-candidate.md#register-your-standby-key). |
| `promotion_start_refused` | Critical | A promotion named this member, but its copy lacks the outgoing epoch's latest head or the vault's latest checkpoint, and no member could provide the gap, which the alert names. The member does not start, and the next promotion passes it over. Follow [A promotion](operator-candidate.md#a-promotion). |
| `promotion_reorged` | Critical | The latest block no longer records the promotion that made this trading server's key the vault's signer. The trading server stopped signing, and marked the reorganisation in `promotion.json`. Restart it. It waits until a final block settles the promotion, and it resumes only once a final block records the promotion. Otherwise, it sets the copy, the resealed keys and `promotion.json` aside as `*.quarantined-<turn>-<position>-<block time>`, pages again, and follows with a new standby key. A restart finishes an interrupted set-aside. A following member raises this alert when the operator in effect's log refuses its copy's tail, and a final block names that tail's key in no signer epoch. The member then sets the copy aside as `*.orphaned-<seq>`, and rebuilds it from the operator's archive. Keep the set-aside files for the owner. Follow [A promotion](operator-candidate.md#a-promotion). |
| `superseded_tail_set_aside` | Warning | A replaced operator, following the member promoted in its place, held instructions that its own key sealed past the last head that its signer epoch posted, or held any instructions when that epoch posted no head. The promoted member's log does not hold them, and a final block shows that the epoch ended. The trading server set its log aside as `<log_dir>.superseded-<seq>`, and rebuilds its copy from the archive of the operator in effect. The message names the instructions dropped, for which clients may have seen answers. Keep the set-aside log for the owner. Follow [A replaced operator coming back](operator-candidate.md#a-replaced-operator-coming-back). |
| `standby_certificates_unreadable` | Warning | A following member's sealed standby certificate file does not open, because the host altered it or gave it another release's file. The member stays promotable, but obtains no certificate for its standby key, so after a promotion it serves the self-signed certificate until the certificate authority issues one. Delete the file, `*standby-certificates.json` in the sealing directory, and restart the member. Follow [Your standby key's certificate](operator-candidate.md#your-standby-keys-certificate). |
| `liveness_task_restarted` | Warning | A member's link or liveness caller stopped or panicked and was restarted, and the member answered and witnessed nothing meanwhile. If the alert repeats, the log lines before it point at the cause. |
| `standby_backfill_refused` | Critical | A standby's copy, backfilled from the archive with its mirrors first, does not replay as a takeover would replay it, because a mirror served altered segments under its own manifest. The standby checks a copy before it first follows onto it, including a copy that an earlier release backfilled. It set the copy aside as `<log_dir>.refused`, and backfilled again from the operator alone, and the `served_by` field is `archive`. While that set-aside copy is there, every start backfills from the operator alone. A copy that the standby then refuses pages with `served_by` set to `operator`, goes to `<log_dir>.refused-operator`, and the standby exits without following. The same happens when the operator's own copy, fetched after a mirror's copy that held no checkpoint, does not replay. A set-aside never replaces an earlier one. With an earlier one there, the refused copy stays in `<log_dir>`, and each start fails until the earlier copy is moved away. While starts keep failing, the episode stays open, and a later start's refusal pages again only when it comes at least `alerts.episode_quiet` after that start began. The alert resolves once a copy replays and the standby follows, or once a copy that holds no checkpoint yet is left for the operator's stream to refill from seq 0. With `served_by` set to `archive`, the archive path reaches the operator's own origin when no mirror answers. The message names the origins tried. Follow [Run the standby](standby.md#run-the-standby). |
| `standby_signal_failed` | Critical | The standby could not read the registry or the vault to detect a promotion, or could not read the vault's signers for its takeover. It reads them again at the next poll. Follow [Run the standby](standby.md#run-the-standby). |
| `standby_takeover_failed` | Critical | A promotion arrived, and the standby's copy could not be finalised. Follow [After a promotion](standby.md#after-a-promotion). |

## Seed relay

| Alert | Level | What it means and what to do |
| --- | --- | --- |
| `seed_missing` | Critical | The turn whose draw deadline passed most recently has no relayed seed. It therefore draws from the last relayed seed, hashed with the turn's number and an Arbitrum block's hash, which the members' trading servers fix within seconds of the deadline. Every member's relay failed or was withheld. The alert resolves once a turn reaches its draw deadline with its seed. Follow [When `seed_missing` fires](seed-relay.md#when-seed_missing-fires). |
| `seed_fallback_lapsed` | Warning | The turn whose draw deadline passed most recently has no relayed seed. Its first fallback fix, `SeedReceiver.fixFallback`, landed in a block whose hash no member recorded before that block passed out of the 256 blocks that `ArbSys` answers for. The turn is never drawn, and the member before it stays named through it. Every member's trading server raises the alert, once per turn. Check why no member's fixer recorded the hash within seconds, with `liveness_caller_fallback_failed` and `liveness_caller_unfunded`, and why the seed was not relayed, with `seed_relay_failed`. The alert resolves at the turn's boundary, when the next turn's draw deadline passes, or at a trading server's first read after a restart past that deadline. Follow [When `seed_missing` fires](seed-relay.md#when-seed_missing-fires). |
| `seed_relay_failed` | Warning | This trading server could not relay a turn's seed that the receiver lacks, or a seed that it relayed had not reached Arbitrum by `seed_relay.resend_after`. | `seed_relayer_unfunded` | Warning | The seed relayer's balance on Ethereum is below `seed_relay.min_balance`, and relays stop once it cannot pay for one. The alert resolves once the relayer is refilled. Follow [When `seed_relayer_unfunded` fires](seed-relay.md#when-seed_relayer_unfunded-fires). |
| `seed_relayer_balance_unreadable` | Warning | The seed relayer's balance on Ethereum has been unreadable for ten minutes. `engine_seed_relayer_balance_eth` stands still, and `seed_relayer_unfunded` cannot fire, while relays keep spending from the key. ## API limits

The trading server raises each of these alerts at most once a minute. While one of them is true, the
API refuses the clients that it concerns.

| Alert | Level | What it means and what to do |
| --- | --- | --- |
| `api_connections_full` | Warning | The connection cap that every client shares is full, and clients are being refused. Look for a flood from a few addresses. A cap that is too low for real traffic is a configuration change, which needs a new release. |
| `api_subscribers_full` | Warning | The cap on stream subscribers is full, and subscribers are being refused. Look for a flood from a few addresses. A cap that is too low for real traffic is a configuration change, which needs a new release. |
| `api_initial_budget_full` | Warning | Accounts that have not deposited share one request budget, and it is exhausted. Look for a flood from a few addresses. |
| `api_paid_declaration_budget_full` | Warning | Wallets with a pending deposit share one budget for eligibility declarations, and it is exhausted. These wallets have paid, so their declarations are exempt from the budgets of wallets that have not, but they share this budget, at the same rate. Look for a few clients that keep repeating declarations that the engine refuses, such as from a restricted region. Their deposits stay pending until a declaration is recorded. |
| `api_declaration_slots_full` | Warning | The screening slots for declarations are full. Look for a flood, and check the access source's latency. |
| `api_screening_slots_full` | Warning | Every screening slot that a request could take is held. Orders receive the status 503 with `screening is at capacity`, and requests to close positions and to withdraw do too once the reserve is taken. The reserve goes only to requests that the account's state shows can reduce risk, one at a time for an account. Each account and each client holds at most its share, and the production slots carry ten times launch flow even when every screening takes the whole `access.timeout`, so look for many wallets or client addresses screening at once, and check the access source's latency. More slots, shares or reserve is a configuration change, which needs a new release. |
| `api_accept_failed` | Warning | The trading server is failing to accept connections. Check the host's limit on open files, and its network. |
| `api_proxy_header_refused` | Warning | A connection from a trusted proxy has no valid PROXY protocol header. Check `[api.proxy_protocol].trusted` against the proxy's real addresses, and check that the proxy sends PROXY protocol version 2 headers. |

## Prometheus rules

`ops/prometheus/engine-node-rules.yml` holds nine rules for the operator's Prometheus. Prometheus
runs outside the enclave, and pages through a receiver other than the trading server's own webhook.
The rules watch what the trading server cannot page about itself, and escalate two certificate
alerts.

| Rule | Fires when | Paired alert |
| --- | --- | --- |
| `EngineNodeDown` | `up{job="engine"} == 0` for a minute. | None, because a trading server that is down cannot page. Follow [Restart and recovery](restart-and-recovery.md). |
| `EngineAlertPagesFailing` | Pages failed or were dropped in the last 15 minutes, as `engine_alert_deliveries_total` counts them. | None, because the rule concerns the pages themselves. Follow [Pages stop arriving](incident-response.md#pages-stop-arriving). |
| `EngineAlertDeliveryFailing` | Three posts failed in 5 minutes, as `engine_alert_attempts_failed_total` counts them. | None, because the rule concerns the pages themselves. Follow [Pages stop arriving](incident-response.md#pages-stop-arriving). |
| `EngineAlertRouteOff` | No delivered bundle holds a severity's webhook URL, so that severity's alerts are only logged, as `engine_alert_route_off` shows. | `secret_missing`, which that route cannot page. Follow [Secrets](key-recovery.md#secrets). |
| `EngineAlertLinesDropped` | Alert lines were dropped before routing, as `engine_alerts_dropped_total` counts them. | None, because the rule concerns the pages themselves. Follow [Pages stop arriving](incident-response.md#pages-stop-arriving). |
| `EngineAlertOutboxOverflow` | Pages were refused at the outbox's size bound, as `engine_alert_outbox_overflows_total` counts them. | None, because the rule concerns the pages themselves. Follow [Pages stop arriving](incident-response.md#pages-stop-arriving). |
| `EngineLogSyncHeld` | `engine_log_sync_held == 1`. | `log_sync_held`, whose page is committed to the alert outbox on the same disk, so that a hold of the whole disk can delay it. Follow [Restart a healthy trading server](restart-and-recovery.md#restart-a-healthy-trading-server). |
| `EngineTlsCertificateMissing` | `engine_tls_certificate_pending == 1` for 30 minutes. | `certificate_pending`. Follow [Certificate renewal failure](certificate-renewal-failure.md). |
| `EngineTlsCertificateExpiring` | The certificate expires within 7 days, as `engine_tls_certificate_not_after_seconds` shows. | `certificate_expiring`. Follow [Certificate renewal failure](certificate-renewal-failure.md). |

Six of the nine rules have no alert behind them that the trading server can page. They exist because
the trading server cannot page that it, or its pages, are not getting through. The Certificate
Transparency watcher exports the same alert metrics, so scrape it in the same job, and the rules
then cover it too.

## Checking this page against the code

Every alert that the code raises appears on this page, and no alert appears that the code does not
raise. To list the alerts that the code raises, run this command from a checkout of the repository:

```shell
rg -o --no-filename 'alert = "[a-z_]+"' crates/node/src --glob '!**/tests/**' --glob '!**/*tests.rs' --glob '!**/test_tracing.rs' | sed 's/alert = //; s/"//g' | sort -u
```

The command prints one alert name per line. It leaves out the alerts that the code raises through a
variable: `custody_rpc_failed`, `custody_chain_unsettled` and `custody_chain_inconsistent`, in
`crates/node/src/custody/stall.rs`, `venue_market_unlisted` and `venue_contract_unlisted`, in
`crates/node/src/feeds/venue/confirm.rs`, and the eight `api_*` alerts, which `ThrottledAlert::new`
raises. `standby_promoted` appears in the code only as a resolution, which ends no alert: it
records that a standby finalised its copy.
